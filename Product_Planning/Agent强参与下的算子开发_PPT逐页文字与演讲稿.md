## 第 1 页｜Agent 强参与下的算子开发

### 页面文字

**Agent 强参与下的算子开发**  
从开发流程、开发者角色到产品 UX 的变化

汇报主题：当 Agent 能参与实现、验证与调优，如何重新组织人、Agent 和工具的协作？

### 演讲稿｜约 1 分钟

今天想讨论的是，随着 Agent 能力增强，算子开发会发生什么变化，以及产品体验需要如何响应。

我们关注的不只是 Agent 能不能生成一段代码，而是一项算子任务如何从需求走到可信交付：它要符合数学语义，能在目标设备上运行，通过正确性验证，并在实际使用场景中获得有意义的性能表现。

这次汇报分成三个部分：首先看开发流程如何变化；接着看开发者的工作重心如何变化；最后讨论产品 UX 应如何支持新的协作方式。这里的产品方向是设计判断，还需要通过真实任务验证。

## 第 2 页｜核心结论：人、Agent 与工具共同完成算子交付

### 页面文字

**流程、角色与体验，需要一起调整。**

| 维度 | 变化方向 |
|---|---|
| 算子开发流程 | 人串联工具 → 围绕目标、候选与证据迭代 |
| 开发者角色 | 亲自完成每一步 → 定义目标、引导探索、验收结果 |
| 产品 UX | 提供工具入口 → 提供共享上下文、过程控制与可信证据 |

**协作原则：人负责目标和取舍；Agent 组织执行与迭代；Toolkit 提供执行能力和验证证据。**

### 演讲稿｜约 1 分 30 秒

先给出整份汇报的结论：Agent 的加入，改变的不只是某一个编码环节，而是流程、角色和产品体验三者之间的关系。

在流程上，过去往往由开发者自己阅读资料、编辑代码、执行命令，再把不同工具的结果拼起来。Agent 强参与后，可以围绕一个明确的任务，持续生成候选、调用工具并根据结果调整。

在角色上，开发者仍然需要算子、编译和硬件知识，但投入会更多地转向定义目标、确定边界、判断实验质量，以及决定最终是否接受结果。

在产品上，交互不能只停留在一个问答窗口。人和 Agent 需要共享同一份任务上下文，用户也要能看到执行状态、检查证据并随时干预。

这里讲的是工作重心迁移，不意味着开发者退出实现过程。复杂语义、关键取舍和最终交付责任仍然需要人承担。

## 第 3 页｜为什么需要重新设计：更快迭代，也要求更强验证

### 页面文字

**算子交付需要同时回答四个问题。**

1. **语义**：实现是否符合目标计算和输入输出契约？
2. **正确性**：是否在目标数据类型、形状和边界条件下通过验证？
3. **性能**：是否在可比条件下达到目标，收益是否稳定？
4. **集成**：是否适用于实际模型及其运行环境？

Agent 可加快“生成 → 执行 → 反馈”的循环，也可能扩大错误假设、薄弱测试和不可靠测量的影响。

**设计要求：任务有边界，结论有证据，开发者能够判断与接管。**

*资料：[KernelBench](https://arxiv.org/abs/2502.10517)；[真实工作负载与验证限制研究](https://arxiv.org/abs/2609.21058)。GPU 研究结论不能直接等同于 PyPTO / 昇腾效果。*

### 演讲稿｜约 1 分 45 秒

为什么算子开发尤其需要重视这件事？因为算子的交付结果不仅是一份代码。它既要符合模型计算语义，也要满足 shape、数据类型、精度和硬件资源约束，最终还需要放回实际模型中检验。

Agent 可以帮助我们更快地写出候选、执行测试、观察反馈并继续调整。但如果一开始的语义理解不准确，或者测试覆盖、误差容忍度和测量条件不充分，Agent 也可能更快地产生看似成功、实际不可靠的结果。

已有 GPU kernel 研究同时关注正确性和相对基线的性能；另有研究指出，薄弱的正确性检查可能让错误实现通过，单个 kernel 的收益也未必转化为端到端收益。这些研究提供了设计线索，但其硬件和测试条件与 PyPTO、昇腾并不相同，不能直接拿来宣称我们的产品效果。

因此，我们要设计的不只是更快的生成环节，还包括清晰的任务边界、独立的验证门禁、可追溯的证据，以及开发者判断和接管的能力。

## 第 4 页｜流程变化：从人工串联，到目标与证据驱动的迭代

### 页面文字

**过去：开发者连接每个步骤和工具**

需求 → 查资料 → 编码 → 编译修错 → 测试 → 调参 → 集成

**Agent 强参与：围绕任务和候选持续迭代**

任务目标与约束 → Agent 建立上下文、生成候选 → Toolkit 编译、验证和测量 → Agent 根据证据调整 → 人审查、决策与交付

- 发生失败时，回到对应环节继续诊断和修改。
- 任务、候选、运行与证据在整个过程中保持关联。
- 编译、正确性、性能、集成分别呈现，不合并为一个“成功”。

### 演讲稿｜约 1 分 45 秒

先看开发流程。传统模式下，一项任务通常由开发者自己拆解。他需要查文档和已有实现，写代码，运行编译，逐条处理错误，构造测试，再通过 profiling 和反复调参完成优化。信息分散在不同文件和工具里，开发者既是执行者，也是整个流程的连接者。

在 Agent 强参与的模式中，起点仍然是明确目标和约束，但 Agent 可以在授权范围内建立工程上下文、生成候选、调用编译和测试，并根据工具反馈继续迭代。工具负责提供可复现的执行和测量结果；开发者在语义、关键取舍和最终验收处作出判断。

这不要求所有任务都走固定向导。遇到编译失败可以回到实现，遇到错值可以回到语义和测试，性能达不到目标则可以继续实验。重要的是，每一次候选和运行都能关联到当时的代码、环境和证据。

同时，我们需要把编译、正确性、性能和集成作为不同状态呈现。编译通过只回答了其中一个问题，不能自动推导出其他阶段也已经通过。

## 第 5 页｜流程分工：人、Agent、Toolkit 各负其责

### 页面文字

| 阶段 | 开发者 | Agent | Toolkit |
|---|---|---|---|
| 定义任务 | 确认语义、目标、范围与预算 | 整理契约，识别缺失信息 | 提供环境、能力和历史基线 |
| 实现与诊断 | 澄清关键歧义，审查方案 | 生成或修改候选，提出定位假设 | 编译、静态检查、采集诊断 |
| 验证与调优 | 确认覆盖充分性，决定取舍 | 组织候选和实验，解释差异 | 正确性测试、设备运行和性能测量 |
| 审查与交付 | 接受、拒绝或继续探索 | 汇总 Diff、证据与风险 | 保存产物、环境和复现信息 |

**共享工作对象：任务 → 候选 → 运行 → 证据 → 决策**

### 演讲稿｜约 1 分 45 秒

把流程进一步展开，可以看到三方各有明确职责。

在任务定义阶段，开发者需要确认 Agent 无法可靠推断的部分，例如数学语义、目标设备、可接受的精度差异和设备预算。Agent 可以整理这些信息、发现缺口；Toolkit 则提供当前环境和已有基线。

进入实现和诊断后，Agent 可以阅读相邻实现、修改代码、调用编译工具，并根据诊断提出修复假设。Toolkit 负责真实执行和返回诊断；人则在语义歧义或重要设计选择上介入。

在验证和调优阶段，Agent 可以组织多个候选，工具负责运行正确性测试、profiling 和 benchmark。开发者需要判断测试是否足够、比较条件是否成立，以及性能与精度或资源消耗之间的取舍。

最后，Agent 汇总改动和证据，工具保存可复现的运行信息，由人决定是否接受。为了让三方看到同一份事实，建议围绕任务、候选、运行、证据和决策来组织状态，而不是只依赖一段聊天记录。

## 第 6 页｜开发者角色变化：更重视定义、判断与验收

### 页面文字

**工作重心从重复执行，转向对目标与结果负责。**

| 工作维度 | 开发者需要更多关注 |
|---|---|
| 定义问题 | 计算语义、输入范围、硬件、精度、性能目标与约束 |
| 引导探索 | 允许的修改范围、实验预算、搜索方向与停止条件 |
| 领域判断 | 用硬件、编译、数值和模型知识判断假设与异常 |
| 审查验收 | Diff、测试覆盖、测量口径、适用范围与剩余风险 |

新手需要理解和验证引导；专家需要原始证据、参数控制以及随时接管的能力。

### 演讲稿｜约 1 分 40 秒

对开发者来说，最明显的变化可能是减少了自己逐条执行命令、手工记录实验的工作；但这并不代表专业知识变得不重要。相反，开发者需要用专业知识更明确地表达什么结果才算正确，以及哪些成本和风险可以接受。

例如，开发者要能判断一个算子的输入范围是否完整、数值容差是否合理，或者一个性能结论是否仅适用于某种 shape。遇到 Agent 提出的优化方案，还需要判断它是否符合硬件特征、是否引入新的资源约束，以及是否值得进入下一轮验证。

不同经验的用户需要不同支持。新手和跨领域开发者需要知道缺了哪些关键信息，如何理解测试结果；经验丰富的工程师则需要查看原始 trace、修改搜索范围、直接编辑代码，或者在必要时完全接管。

因此，产品应该支持不同程度的委托和介入，而不是假设所有人都只通过自然语言完成工作。

## 第 7 页｜UX 变化：从工具入口，走向可管理的任务体验

### 页面文字

**围绕开发者的五个问题组织体验。**

| 用户问题 | 产品需要提供 |
|---|---|
| 要做什么？ | 可编辑的任务目标、约束、验收条件和已关联上下文 |
| 进行到哪里？ | 当前动作、进度、阻塞项、设备排队与预算 |
| 如何控制？ | 任务范围和授权边界；暂停、取消、接管与预算调整 |
| 能否相信？ | 事实、推断与实测的区分；从结论下钻到原始证据 |
| 如何继续？ | 跨 IDE、CLI、Studio 的任务状态、运行与产物衔接 |

**同时面向人和 Agent：人获得可理解的状态，Agent 获得稳定、结构化的工具接口。**

### 演讲稿｜约 1 分 45 秒

接下来讨论产品 UX。一个常见做法是在现有工具旁边增加聊天窗口，但如果任务状态仍然散落在文件、命令行和不同工具里，用户还是需要自己重建上下文，也很难判断 Agent 究竟做到了哪一步。

我们建议把体验组织在任务之上。用户发起任务后，能够看到目标、约束和验收条件；执行过程中，能够看到当前动作、设备排队、预算和阻塞项；需要干预时，可以暂停、接管或者调整范围。

结果出现后，用户不只看到一句“已经优化”，而是可以检查它对应的代码变化、正确性结果和性能证据，并区分哪些是源码事实、哪些是 Agent 推断、哪些来自设备实测。切换到 IDE、CLI 或 Studio 时，这些上下文仍然可以延续。

同时，Agent 本身也是工具使用者。它需要稳定的工具输入、结构化输出和清晰错误信息。这样人和 Agent 才能基于同一份运行事实协作。这里描述的是产品设计方向，不意味着现有系统已经实现。

## 第 8 页｜UX 关键时刻：让判断发生在正确的节点

### 页面文字

| 关键时刻 | 用户看到什么 | 用户可以做什么 |
|---|---|---|
| 启动任务 | 目标、硬件、shape/dtype、精度、范围和缺失信息 | 补充或修改任务契约 |
| 执行与干预 | 当前动作、失败原因、预算和下一步 | 暂停、调整边界或接管 |
| 审查候选 | Diff、正确性覆盖、基线与候选的同口径对比 | 下钻证据、要求补测或继续探索 |
| 验收与复用 | 目标达成情况、未覆盖项、风险和复现方式 | 接受、拒绝或交接任务 |

**日常已授权操作尽量连续；涉及重要取舍、超预算或超范围时，提供清晰的决策信息。**

### 演讲稿｜约 1 分 45 秒

把刚才的原则落到交互上，可以聚焦四个关键时刻。

第一个是启动。Agent 可以从代码和环境中预填信息，但必须把推断和已确认条件区分开。用户需要能看到目标硬件、输入范围、精度要求和预算，并补全缺失项。

第二个是执行。用户应该知道 Agent 正在做什么、已经尝试过什么，以及失败发生在哪个环节。遇到长时间排队或者方向不对，可以暂停、改变边界或者自己接管。

第三个是审查。对于一个推荐候选，界面要把代码 Diff、正确性覆盖和性能对比放在一起。比较结果还要说明设备、输入和测量条件；对于未覆盖的 shape 或没有完成的检查，要明确显示。

第四个是验收与复用。用户需要知道目标是否达成、还剩哪些风险、如何复现，然后决定接受、拒绝或者继续探索。

这里的控制并不等于每一步都打断。已在授权范围内的日常操作可以连续执行；当出现精度取舍、超出预算或修改范围变化时，再把影响和选项交给人。

## 第 9 页｜场景示例：一次 RMSNorm 性能优化任务

### 页面文字

**任务：在指定设备和输入范围内降低延迟；保持接口与数值语义，最多尝试 20 个候选。**

| 阶段 | Agent 与 Toolkit | 开发者与产品交互 |
|---|---|---|
| 建立基线 | 读取实现与测试，运行并记录基线 | 确认输入、容差、设备和测量条件 |
| 搜索候选 | 提出分块等假设，编译并验证候选 | 查看候选、进度与预算；必要时接管 |
| 对比验收 | 展示通过正确性检查的候选及性能分布 | 审查 Diff、覆盖和未测项，决定接受或补测 |

**验收依据：代码变化 + 正确性覆盖 + 可比的性能证据 + 适用范围。**

*本页为虚构示例，不代表实际产品能力或实测收益。*

### 演讲稿｜约 1 分 45 秒

用一个虚构的 RMSNorm 优化任务把前面的变化串起来。

开发者提出目标：在指定设备和输入集合上降低延迟，保持已有接口和数值语义，最多尝试二十个候选。Agent 先读取实现、现有测试和运行记录，整理出 shape、数据类型、容差和设备条件。开发者检查这些信息，补充缺失项，并确认任务范围。

接着，Toolkit 执行基线测试，记录代码版本、输入和测量条件。Agent 结合 profile 提出例如分块参数的优化假设，在预算内生成候选。每个候选先经过编译和正确性检查，再对通过检查的候选进行性能测量。失败的候选保留失败原因，不能直接进入合格排名。

最后，界面并列展示候选的代码变化、测试覆盖和延迟分布。如果某个候选只验证了部分 shape，就明确标出适用范围，而不是简单展示一个最快数字。开发者可以要求补测、继续探索，或者在证据充分时接受候选。

这个示例体现了三个变化：流程有了反馈闭环，开发者把重点放在目标和验收上，产品则围绕任务、证据与控制组织信息。

## 第 10 页｜落地方向：先建立可信闭环，再扩大自动化范围

### 页面文字

| 阶段 | 优先建设 | 要回答的验证问题 |
|---|---|---|
| 1. 受控执行 | 任务契约、编译/测试接口、Diff、运行关联、暂停与接管 | 用户能否理解 Agent 的工作并有效接管？ |
| 2. 证据驱动诊断 | 关联源码、编译和运行；呈现失败与复现信息 | 能否更快找到问题，减少缺乏证据的修复？ |
| 3. 受预算调优 | 基线、候选、设备预算、正确性门禁和可比性 | 能否在相同成本条件下得到可复现收益？ |
| 4. 集成与复用 | 模型级验证、结果包、审查记录和共享基线 | 结果能否用于真实 workload 并由团队复用？ |

**验证维度：可信交付时间｜人工介入｜回归与复现｜设备成本｜用户判断与接管能力**

### 演讲稿｜约 2 分钟

最后看落地顺序。建议第一步先建立受控执行的最小闭环：明确任务契约，为编译和测试提供结构化接口，把代码变化和实际运行关联起来，并让用户能够看到状态、暂停和接管。这个阶段首先验证协作是否可理解、可控制。

第二步加强证据驱动的诊断，把源码、编译和运行中的关键信息连接起来。我们需要验证的是，用户和 Agent 能否更快定位问题，以及修复是否有足够证据支持。

第三步再扩大到受预算约束的性能搜索。产品需要管理基线、候选和设备成本，保证正确性门禁和性能比较口径成立。性能提升必须能够复现，也要同时观察设备时间和回归风险。

第四步连接模型集成和团队复用。算子在局部测试中有效，还需要确认它在真实 workload 中的价值，并把结果、环境、风险和决策交给后续维护者。

验证时建议使用真实任务作对照，记录从提出任务到可信交付的时间、人工介入、回归、复现率和设备成本，也观察开发者能否识别证据缺口并接管。当前不预设具体收益数字，通过试点决定哪些能力值得优先投入。

今天希望形成的共识是：Agent 强参与带来的产品机会，在于让人、Agent 和工具围绕一项可验证的算子任务持续协作，并让开发者始终掌握关键判断和交付结果。
