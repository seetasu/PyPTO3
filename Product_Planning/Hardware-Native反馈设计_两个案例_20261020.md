# Hardware-Native 诊断案例：片上空间超限后，告诉用户该怎么改

> 整理日期：2026-10-20
> 指导思路：不是把昇腾硬件细节全部倒给用户，而是在错误发生后，把相关约束翻译成可理解、可行动的反馈。
> 案例来源：[hw-native-sys/pypto#630](https://github.com/hw-native-sys/pypto/issues/630)。文中的诊断文案与交互为产品设计扩展，不代表当前系统已实现。

## 案例概览

**用户正在调 DeepSeek V3.2 decode 算子。** 把 `KV_LORA_RANK` 从 128 提高到 512 后，编译在 `AllocateMemoryAddr` 阶段失败。

编译器报告 Right buffer 使用 **98,304 B**，超过平台上限 **65,536 B**；日志还带有变量使用位置、生命周期区间、`space` 编码和 buffer 大小等底层信息。数字本身告诉用户“有一块片上空间不够”，却没有直接回答：**这次参数改动如何变成了这项占用，用户应该在代码的哪一维做调整？**

这个案例要解决的不是诊断真假，而是诊断到用户动作之间的翻译缺失。Issue 给出的直接修法是：当 `KV_LORA_RANK_CFG` 增大时，需要增加一层沿该维度的循环分块。

---

## 1. 用户问题：报错后，他必须自己补齐一条硬件推理链

### 用户的任务变化

用户把 `KV_LORA_RANK` 从 128 调到 512，维度扩大为原来的 4 倍。已有代码仍按原来的 tile 结构处理这段数据，因此一个 tile 需要容纳的数据增加，触发片上 buffer 容量检查失败。

### 系统给出的实际反馈

```text
Verification failed after 'AllocateMemoryAddr'
Right buffer usage (98304 bytes) exceeds platform limit (65536 bytes)
Location: deepseek_v3_2_decode_front.py:390:20
```

同一段输出还包含类似这样的底层生命周期信息：

```text
Variable _t64_tile has 1 use statements
Lifetime for sharing group ... [3, 4] space=1 size=32768
Variable token_row_0_tile has 1 use statements
Lifetime for sharing group ... [4, 5] space=1 size=16384
```

### 用户还需要自己知道什么

要从这些信息走到可用改法，开发者需要自行完成几步关联：

1. 知道 Right buffer 是目标硬件上的受限片上空间，64 KiB 是这次编译所依据的容量上限。
2. 把 `98,304 B > 65,536 B` 与这次 `KV_LORA_RANK` 的增大联系起来，而不是把它当成一个独立的 buffer 错误。
3. 理解 PTO 3.0 的 tiling 需要在 DSL 中表达；大维度不一定会像旧流程那样自动展开成循环。
4. 从所有可能的参数中找出正确的修改方向：沿 rank 维分块，让每个 tile 处理较小的一段。
5. 修改后再次编译、验证正确性，并确认分块后没有把压力转移到 Mat、Vec 等其他片上空间。

因此，系统虽然给了硬件数字和内部日志，**从硬件约束到代码结构的关键一步仍然由用户完成**。

---

## 2. 反面解决思路：继续给资料，或只把错误换句话说

### 反面 A：把 Right buffer 的硬件介绍写得更长

补充更多容量表、存储层级、地址分配算法、变量生命周期和 `space` 编码解释。用户会得到更多硬件知识，但仍要自己判断这些信息与 `KV_LORA_RANK` 的关系，也仍要自己找出应当新增哪一层循环。

### 反面 B：只把错误信息改成中文

例如：“Right buffer 超过平台限制，请减小 tile。”这比纯英文更易读，却没有回答两个关键问题：**哪个 tile 与本次参数有关？怎么减小才不会破坏原来的计算语义？**

### 反面 C：泛泛建议“缩小 tile”或“调整分块”

这把搜索空间仍留给用户。用户可能反复改 M、K、N 或其他配置，既无法确认改动是否对应根因，也可能让性能下降或在另一个片上空间再次失败。

### 反面 D：只命令用户“加一层循环”

如果不说明应沿 `KV_LORA_RANK` 这一维分块，也不提供适用范围与验证方式，用户仍需猜测分块轴、块大小、累积/写回位置，以及修改后哪些资源需要复查。

---

## 3. 合理解决思路：把硬件数字变成代码决策

诊断应按开发者做决定的顺序组织信息：**改了什么 → 触发了什么资源约束 → 应调整哪里 → 修改后如何确认。**

### 第一步：先用一句话解释失败

将“Right buffer usage 98,304 B > limit 65,536 B”翻译为：

> `KV_LORA_RANK` 从 128 增至 512 后，当前 tile 覆盖的数据量过大，目标片上的 Right buffer 已超过可用容量。

这句话把硬件资源名、超限数字和用户刚改的参数连在一起。`AllocateMemoryAddr`、`space` 编码等编译器术语可以保留在“技术详情”中，不必成为理解问题的前置条件。

### 第二步：把建议落到应修改的维度

Issue 的直接修法是沿 `KV_LORA_RANK_CFG` 增加分块循环。诊断可以指出修改方向，而不替用户决定唯一的块大小：

```text
当前：一个 tile 覆盖较大的 KV_LORA_RANK 区间
建议：沿 KV_LORA_RANK 轴拆成较小区间，循环处理各块
```

这是设计表达示意，不是可直接复制的 PyPTO 代码。具体块大小、累积方式和写回位置需要结合该算子的计算语义与目标配置确定。

### 第三步：提供可验证的调整范围

如果编译器能够从当前 IR 和目标硬件推算候选值，应展示：

- 当前 tile 需要的 Right buffer：98,304 B；目标上限：65,536 B。
- 沿 rank 维分块后，每个候选 tile 的预计占用。
- 预计同时变化的 Mat、Vec 等资源占用，避免只解决一个 buffer 后立刻撞上另一个限制。
- 是否需要额外的跨块累积、同步或尾块处理；无法确定时标成待验证，不假装已经算出正确实现。

如果编译器无法可靠推算块大小，应提供明确的建议方向和一个可运行的分块示例，再让用户验证数值结果与性能。

### 示例诊断文案

> **当前 tile 超出片上 Right buffer 容量**
> 你将 `KV_LORA_RANK` 从 128 调到 512。当前 tile 需要 98,304 B Right buffer，高于本目标的 65,536 B 上限。
> **建议**：沿 `KV_LORA_RANK` 维度分块，并在循环中逐块处理。先查看建议分块对 Right、Mat、Vec 空间的预计占用，再验证跨块计算的正确性。
> 技术详情：查看触发检查的源码位置、相关 tile、地址与生命周期日志。

以上文案属于产品设计扩展。Issue 当前提供的是编译失败和低层报告，并未显示系统已经生成这种用户级解释或自动计算候选分块。

## 4. 这个案例的可复用判断

| 诊断层次 | 需要回答的问题 | 本案例的内容 |
| --- | --- | --- |
| 失败结果 | 发生了什么？ | Right buffer 98,304 B 超过 65,536 B |
| 关联上下文 | 为什么现在发生？ | `KV_LORA_RANK` 从 128 增至 512，原 tile 不再适配 |
| 相关硬件知识 | 哪条约束与当前修改有关？ | 当前目标的 Right buffer 容量有限 |
| 用户动作 | 该改代码的哪里？ | 沿 `KV_LORA_RANK` 维分块循环处理 |
| 验证闭环 | 改完如何确认？ | 检查其他片上空间、尾块与跨块语义，再做正确性和性能验证 |
| 深层证据 | 想排查更多时看什么？ | `AllocateMemoryAddr` 阶段、源码位置、buffer 生命周期和地址报告 |

**产品判断**：好的硬件诊断不以“解释了多少硬件名词”为标准，而要看用户能否从报错直接找到与本次修改有关的约束和下一步。底层报告继续保留，系统先替用户筛选和关联。
