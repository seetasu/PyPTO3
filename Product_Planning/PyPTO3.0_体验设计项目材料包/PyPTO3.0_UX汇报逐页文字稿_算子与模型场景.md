## 核心推导

产品希望支撑算子与模型任务 → 识别用户跨层理解执行、跨工具组织工作的需求 → 形成两个设计命题：目标硬件如何影响决策，Agent 参与后任务如何组织 → 分别讨论 Hardware-Native 与 Agent → 回到场景验证。硬件要求源于任务本身；Agent 是值得研究的参与者，两者不互为前提。具体痛点和 Agent 使用情况需以研究与案例核实。

## 面向体验设计领导的讲述重点

产品背景、定义和价值用于建立设计语境，控制在支撑设计判断所需的深度。汇报重点是：复杂计算开发中用户如何理解和行动；设计如何连接硬件反馈、跨层信息与人机协作；设计交付和验证如何体现专业贡献。业务收益作为待验证目标，避免以立项或功能规划代替体验分析。

## 使用与证据约定

本稿依据本次讨论的产品范围及仓库现有规划整理。算子开发和模型推理是本次汇报的重点讨论范围；模型训练是未来可能扩展的方向，具体边界和计划待产品确认。文中“产品期望”“设计建议”“场景设定”不等同于已经交付的功能或已验证的效果。2.0 与 3.0 的正式定义、能力状态及竞品结论须在正式汇报前逐项核实；涉及具体产品和版本的横向对比应补充来源、日期与适用范围。场景是说明设计逻辑的示例，不作为真实项目成果或性能数据。

## 第二部分：能力建设范围与横向对比

### 第 8 页｜能力地图：按任务层次组织建设范围

**核心内容**

- 算子层：表达、编译、正确性、性能分析、调优与交付。
- 推理层：接入、运行、观测、精度和性能分析、优化验证。
- 跨场景：环境与版本、运行记录、证据关联、自动化接口与协作。
- 训练方向：依据用户研究与产品规划补充，不在此假定完整能力。

**讲述**

能力地图展示为完成任务需要讨论的范围，不表示每项能力均已实现或列入建设承诺。正式材料应为每项标注状态和责任方，明确哪些需要其他工具链共同支撑。

**过渡语**

有了统一的能力框架，才能选择合适的参照对象，判断基础和差距。

### 第 9 页｜横向对比：在相同任务和产品边界下比较

**核心内容**

- 算子开发对比：表达、编译、验证、硬件分析和调优。
- 模型推理对比：模型接入、执行观测、诊断和优化验证。
- 跨层体验对比：上下文传递、模型到算子下钻、结果交接。
- 对比表注明对象、版本、来源、核查日期，以及功能与体验证据的区别。

**讲述**

不同工具的产品边界和目标用户可能不同，不能只比较功能数量。建议使用现有竞品研究作为素材，正式呈现前重新核实具体版本与结论；若没有同口径证据，就不作领先性判断。

**过渡语**

对比的目的不是完成一张表，而是帮助我们确定建设优先级。

### 第 10 页｜从对比得到三类建设判断

**核心内容**

- 基础门槛：缺失后会阻碍用户完成核心任务的能力。
- 体验差距：能力存在，但用户难以发现、理解或串联。
- 特色机会：与昇腾硬件、跨层分析和任务协作相关的方向。
- 具体排序需结合真实用户痛点、工程状态和同口径竞品证据确认。

**讲述**

这三类不是预设的竞品结论，而是整理研究结果的框架。最终应将每项判断对应到具体场景、证据和建设责任，避免把设计愿景包装成已实现的差异化。

**过渡语**

能力地图回答了需要建设什么，接下来要从任务中提炼两个问题：用户如何理解目标硬件上的执行，以及如何组织人和工具的协作。

## 第三部分：Hardware-Native 与 Agent 的设计输入

### 第 11 页｜从任务要求到设计命题：执行如何被理解，工作如何被组织

**核心内容**

- 算子与模型任务在目标设备执行：用户需要理解硬件约束及其影响，由此引出 Hardware-Native。
- 完成任务需要跨工具组织工作；Agent 可参与部分环节，由此需要研究任务委托、执行与交接。
- 硬件是任务本身的专业要求，Agent 是值得验证的协作方式变化；两者并行，不互为前提。
- 人、工具和领域专家继续承担各自职责。

**讲述**

从能力地图看，能力存在只是第一步，开发者还要把它用于具体判断。任务在昇腾设备上执行，需要理解硬件约束和结果；任务也跨工具、跨角色组织，Agent 的参与可能改变部分工作的分配与交接。前者即使没有 Agent 也成立，后者需要结合用户实际采用情况验证。

**过渡语**

先从 Hardware-Native 开始，看看它在不同任务层次中意味着什么。

### 第 12 页｜Hardware-Native：让硬件事实进入开发决策

**核心内容**

- 算子层：分块、数据搬运、资源使用、并行与同步会影响执行。
- 推理层：计算路径、调度和资源使用影响模型整体表现。
- 用户需要理解当前选择受到什么约束、产生什么结果、下一步如何验证。
- 具体规则和结论必须绑定目标硬件、工具链版本与测量条件。

**讲述**

不同实现可能表达同一计算，但在目标设备上的表现不同。设计要把相关硬件信息放在用户作出选择的位置，并允许专家深入查看细节。

**过渡语**

硬件知识只有与当前任务和实际证据连接起来，才能成为可操作的反馈。

### 第 13 页｜跨层理解：从模型现象到计算与硬件证据

**核心内容**

- 从模型任务和整体表现出发，逐步缩小问题范围。
- 在有证据支持时，下钻到计算路径、算子、编译或运行细节。
- 将局部发现带回模型层，验证是否改善整体目标。
- 数据不足时明确缺口，不将相关性直接表述为原因。

**讲述**

这里展示的是设计希望支持的分析路径，不意味着每个问题都来自算子，也不意味着所有跨层映射已存在。数据关联、诊断准确性和工程接口需要后续验证。

**过渡语**

硬件说明了开发者需要什么专业判断。再看另一面：完成判断通常要收集上下文、调用工具并组织实验；当 Agent 参与这些工作时，用户的协作需求可能发生什么变化？

### 第 14 页｜Agent 参与：从一次回答走向持续任务协作

**核心内容**

- 算子任务：可探索需求整理、候选形成、验证与调优编排。
- 推理任务：可探索上下文整理、观测分析和诊断路径建议。
- 人确定目标、约束和最终取舍；工具执行检查与测量；Agent 组织辅助工作。
- 能力和采用程度因任务、用户和环境而异，需用实际案例验证。

**讲述**

设计不假设所有任务都由 Agent 自动完成。用户可以选择手工、辅助或更充分的委托；工具结果应能被核对，而 Agent 的建议需要说明依据与不确定性。

**过渡语**

当工作可以被委托，体验的重点便延伸到执行过程和交接。

### 第 15 页｜人机协作：让委托、审阅和接管成为明确动作

**核心内容**

- 委托前：说明目标、上下文、约束和允许的操作。
- 执行中：了解当前状态、已执行动作、结果和异常。
- 审阅时：查看候选、证据、未覆盖风险和可比较条件。
- 必要时：调整方向、暂停、接管，并保留交接记录。

**讲述**

已有工程问题如硬件约束难理解、跨层定位困难，并非由 Agent 引起。Agent 可能放大实验和版本管理压力，也带来委托、授权和接管等新的交接需求；这些影响需要在具体任务中验证。

**过渡语**

接下来把硬件与 Agent 两条线索带回同一项用户任务，观察它们如何共同影响体验。

### 第 16 页｜在真实任务中汇合：专业反馈支撑协作决策

**核心内容**

- 模型推理出现性能问题，用户或 Agent 先整理目标、环境和观测结果。
- 依据证据缩小范围；必要时进入相关计算或算子分析。
- 工具提供编译、正确性及运行反馈；人审阅方案和证据。
- 修改后回到模型层验证；这是示例路径，不代表所有问题都来自算子。

**讲述**

这一例子把前述两个设计命题放到同一任务中：硬件反馈帮助判断执行问题，Agent 可以协助组织信息和实验，人需要判断方向和结果。体验的价值体现在这些参与方能否围绕同一任务衔接，而不是单独展示一个 AI 功能。

**过渡语**

为了确定哪些体验最值得设计，我们分别梳理算子和模型推理的用户旅程。

## 第四部分：用户任务、UX 机会与场景优先级

### 第 17 页｜两条任务旅程：目标不同，上下文需要连接

**核心内容**

- 算子：明确需求 → 形成实现 → 编译验证 → 性能优化 → 交付维护。
- 推理：模型接入 → 运行观测 → 定位问题 → 优化比较 → 集成与交付。
- 算子侧需要深入实现与硬件；推理侧从整体目标识别问题范围。
- 共同需求：明确目标、关联证据、验证结论和交接结果。

**讲述**

两条旅程不应合并成单一流程。推理可能需要进入算子层，也可能在其他环节解决问题；算子开发则需要在适用时回到模型任务确认价值。

**过渡语**

将任务中的困难和判断归纳后，可以得到跨场景的设计机会。

### 第 18 页｜六类 UX 机会与优先场景

**核心内容**

- 任务上下文连续；执行过程可理解；问题可跨层定位。
- 比较与取舍有依据；人机协作可掌控；结果可交付和复现。
- 优先探索：模型推理诊断与优化、算子性能优化与验证。
- 场景排序需结合用户痛点、真实数据、工程可行性和业务优先级确认。

**讲述**

这些机会既适用于共同能力建设，也需要具体场景解释。训练方向可借鉴问题框架，但用户、任务和优先级仍需研究，不在本次直接套用推理流程。

**过渡语**

先看模型推理场景：用户从整体目标出发，如何找到有依据的分析路径。

## 第五部分：典型场景设计探索

### 第 19 页｜模型推理场景：从整体表现进入问题

**核心内容**

- 场景设定：一次模型推理运行没有达到预期表现。
- 用户先确认模型、输入、环境、目标指标和比较基线。
- 设计呈现整体运行状态、关键指标及证据是否完整。
- 场景为设计示例；指标、界面与能力以实际数据和原型为准。

**讲述**

推理工程师首先要判断发生了什么，而不是立即进入某个算子。将目标和条件放在一起，可以帮助用户识别哪些结果可以比较，哪些结论还缺少依据。

**过渡语**

看到整体表现之后，下一步是缩小问题范围，而不是直接假定原因。

### 第 20 页｜模型推理场景：定位问题并保留跨层上下文

**核心内容**

- 依据运行观测，查看相关阶段、计算路径或资源使用。
- Agent 可整理线索并提出诊断路径；用户查看证据和不确定性。
- 在有依据时下钻到算子、编译或硬件执行，并保留原始模型上下文。
- 信息不足时展示缺口和下一步采集建议，不给出确定归因。

**讲述**

关键体验是从一个现象进入可核对的分析路径。不同专家可以共享同一个任务和运行条件，减少重新建立上下文；跨层关联的实际可用性仍依赖工程数据。

**过渡语**

找到可能的改进方向之后，还需要判断优化是否真的改善了模型任务。

### 第 21 页｜模型推理场景：回到整体验证优化效果

**核心内容**

- 对比前确认模型、输入、环境、版本与测量口径。
- 同时查看正确性或精度、性能与资源变化。
- 展示局部变化和模型级结果的关系，以及尚未覆盖的条件。
- 由用户决定接受、继续实验或保留原方案。

**讲述**

局部操作更快不自动等于模型整体更好。设计应帮助用户确认结果的比较资格和适用范围，再交给团队决定是否采用。

**过渡语**

当分析确实需要深入算子实现时，接下来的场景展示更细粒度的硬件判断和验证过程。

### 第 22 页｜算子场景：明确目标、约束与可信基线

**核心内容**

- 场景设定：在接口和正确性要求不变的前提下优化算子延迟。
- 用户明确输入范围、目标硬件、实验预算与验收条件。
- 系统整理实现、版本、测试和基线，并标出缺失信息。
- Agent 的执行范围和操作权限由任务上下文明确约束。

**讲述**

先定义完成条件，才能判断后续候选是否有价值。该页展示拟议的任务组织方式，并不预设现有工具已经提供全部接口。

**过渡语**

任务边界明确后，需要理解当前实现与目标硬件之间可能存在什么约束。

### 第 23 页｜算子场景：用硬件反馈形成和检验候选

**核心内容**

- 展示与当前选择相关的资源约束、编译反馈或运行线索。
- 用户或 Agent 提出候选，说明假设、改动范围和验证计划。
- 工具执行编译、正确性检查与受约束的性能测量。
- 显示失败原因、证据来源和待验证项；不把建议当成已证实收益。

**讲述**

Hardware-Native 的价值是帮助用户理解为何值得尝试某个方向、限制在哪里，以及如何验证。Agent 可以组织候选，领域规则和设备结果仍由相应工具与专家提供。

**过渡语**

候选执行之后，用户还需要能够比较、作出取舍，并将结论交付出去。

### 第 24 页｜算子场景：审阅结果、接管过程并交付

**核心内容**

- 对比候选与基线的正确性、性能、代码差异和适用条件。
- 用户可接受、拒绝、继续尝试或接管；保留过程与停止原因。
- 交付包含版本、环境、测试结果、未覆盖风险及复现入口。
- 如来源于模型任务，回到模型层确认实际影响。

**讲述**

结果是否可信，取决于验证是否覆盖关键条件、性能数据是否可比较、后续团队能否复现。页面应帮助用户看到这些依据，而不是只显示最快的数字。

**过渡语**

两个场景分别体现整体分析与专业深度，下面总结它们的关系和方案成熟度。

### 第 25 页｜场景关系与方案成熟度：先证明一条链路

**核心内容**

- 模型场景关注整体目标和定位；算子场景深入实现与硬件反馈。
- 二者可在有依据时衔接，局部优化需回到整体任务验证。
- 每项展示标注：已有能力、设计原型、工程依赖或待验证假设。
- 下一步选择真实案例贯通数据和操作，验证能否完成任务。

**讲述**

原型展示的是可讨论的交互方案，不等于端到端能力已经实现。需要与工程和领域专家核实各环节数据与接口，再邀请目标用户评估。

**过渡语**

场景中的体验由界面、任务状态、Agent 行为和工具反馈共同决定，因此 UX 交付也需要覆盖这些对象。

---

## 第六部分：Agent 模式下的 UX 设计实践

### 第 26 页｜UX 交付：从页面扩展到任务与协作规则

**核心内容**

- 用户任务与旅程：目标、关键判断、角色和交接。
- 信息与状态模型：模型、算子、运行、候选和证据的关系。
- 人机协作规则：委托范围、执行反馈、审阅、异常与接管。
- 跨层交互原型与验证方案：从整体观察到下钻，再回到决策。

**讲述**

设计产出应解释用户如何理解与控制任务，也要让工程团队知道状态、动作和反馈如何衔接。交付物按项目需要选择，不要求所有场景采用同一种界面。

**过渡语**

这些设计需要多个专业团队共同实现，因此必须把职责与依赖说清楚。

### 第 27 页｜设计边界与验证：与产品、工程和领域专家共建

**核心内容**

- UX：从用户任务出发，定义跨层信息、关键判断、交互与协作规则。
- 产品：目标、范围、优先级和业务验收。
- Agent、工具链和硬件团队：实现能力、提供可靠结果与专业规则。
- 验证用户能否理解和接管、链路是否贯通、算子与模型任务效果是否改善。

**讲述**

用真实任务分别验证理解、工程可行性和任务结果。若要衡量体验设计贡献，可在可行条件下比较现有流程、现有 AI 辅助流程与新体验，控制任务、环境和验收标准。

**过渡语**

最后，将这些设计与协作要求收敛为下一阶段可以执行的工作。

## 结尾：项目推进与收束

### 第 28 页｜下一步：聚焦真实任务，贯通并验证

**核心内容**

1. 确认产品定位、2.0/3.0 差异、能力状态与跨团队边界。
2. 选择算子和模型推理的代表性任务，明确用户、数据和成功标准。
3. 贯通关键任务状态、工具调用及证据，完成原型与工程联合验证。
4. 持续研究模型训练任务，明确用户需求与未来产品范围。

**讲述**

PyPTO 3.0 UX 要帮助开发者在不同层次的计算任务中理解执行、作出判断并有效协作。当前先围绕算子与推理验证真实任务，再根据证据扩展能力和场景。

**结束语**

请围绕优先任务、设计贡献和验证方式形成共识，与产品、工程及领域专家共同推进场景验证。
