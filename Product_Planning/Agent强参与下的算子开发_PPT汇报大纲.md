# Agent 强参与下的算子开发：汇报 PPT 大纲

> 建议对象：产品、研发与体验设计负责人｜建议时长：15–20 分钟｜主报告 10 页  
> 定位：讨论未来产品方向；以下体验与收益为设计判断，尚需真实任务验证。

## 汇报主线

**Agent 能够参与实现、工具调用和实验迭代，改变了算子开发的分工：流程围绕任务与证据组织，开发者更多负责目标与判断，产品需要提供可理解、可控制、可验证的协作体验。**

叙事顺序：背景与结论 → 流程变化 → 开发者变化 → UX 变化 → 案例与落地。

---

## P1｜封面

**标题：Agent 强参与下的算子开发**  
**副标题：从开发流程、开发者角色到产品 UX 的变化**

- 汇报目的：明确 Agent 参与后，算子开发如何协作，以及产品应如何响应。
- 建议画面：开发者、Agent、Toolkit 围绕一个算子任务协作的简图。

## P2｜核心结论：算子开发正在转向人、Agent 与工具的协作闭环

**页面要传达：Agent 带来的变化覆盖工作流程、人的职责和产品体验。**

| 三个维度 | 主要变化 |
|---|---|
| 算子开发流程 | 从人串联工具，转向围绕目标、候选与证据持续迭代 |
| 开发者角色 | 从亲自执行每一步，转向定义目标、引导探索和验收结果 |
| 产品 UX | 从提供工具入口，转向提供共享上下文、过程控制和可信证据 |

- 汇报提示：强调这是工作重心变化；复杂语义、关键取舍和最终交付仍由人负责。
- 建议画面：三张并列变化卡片，底部用一条闭环串联。

## P3｜为什么要变：Agent 能加快迭代，也放大验证问题

**页面要传达：算子开发的结果必须同时经得起语义、正确性、性能和集成检验。**

- Agent 能读取工程、生成候选、调用编译与测试，并根据反馈继续修改。
- 算子开发涉及 shape、dtype、精度、编译、硬件资源与模型集成，代码生成只是其中一环。
- 编译通过不等于正确；局部 kernel 更快也不必然带来模型级收益。
- 设计命题：让 Agent 的每次尝试有边界、结果有证据、用户能判断和接管。

**建议画面**：左侧“生成—执行—反馈”循环，右侧“正确性 / 性能 / 集成”三个检验点。  
**依据**： [KernelBench](https://arxiv.org/abs/2502.10517)、[真实工作负载与验证限制研究](https://arxiv.org/abs/2609.21058)。研究基于 GPU 场景，不能直接推断 PyPTO / 昇腾效果。

## P4｜流程变化：从人工串联步骤，到目标和证据驱动的迭代

**页面要传达：工作流的组织方式改变，算子开发的交付标准保持独立。**

**过去的典型路径**  
需求 → 查资料 → 人工编码 → 编译修错 → 测试 → 人工调参 → 集成

**Agent 强参与的路径**  
任务目标与约束 → Agent 建立上下文和候选 → Toolkit 编译、验证、测量 → Agent 基于证据迭代 → 人审查、决策和交付

- 失败可回到相关环节重新迭代；任务状态跨步骤保留。
- 编译、正确性、性能、集成分别呈现，不能以单一“成功”替代。

**建议画面**：上下两条泳道，突出由线性串联转向反馈闭环；在闭环上标出人的目标与验收节点。

## P5｜流程分工：人、Agent、Toolkit 各自承担什么

**页面要传达：Agent 组织候选和实验，Toolkit 产生执行结果，人负责关键工程判断。**

| 阶段 | 人 | Agent | Toolkit |
|---|---|---|---|
| 任务定义 | 确认语义、目标、范围和预算 | 整理契约，识别缺失信息 | 提供环境和历史基线 |
| 实现与诊断 | 处理关键歧义，审查方案 | 编码、编译修复、定位假设 | 编译、检查、采集诊断 |
| 验证与调优 | 确认验证充分性及取舍 | 生成候选、组织实验 | 正确性测试、设备运行和性能测量 |
| 交付 | 决定是否接受 | 汇总变化、证据及风险 | 保存运行产物与复现信息 |

**建议画面**：三行泳道，底部贯穿“任务 → 候选 → 运行 → 证据 → 决策”。

## P6｜开发者角色变化：从主要执行者到目标与结果的负责人

**页面要传达：开发者减少重复操作，增加对问题定义、验证和取舍的投入。**

| 工作维度 | 重心变化 |
|---|---|
| 问题定义 | 从描述实现步骤，更多转向明确语义、约束和验收条件 |
| 日常开发 | 从手工串联命令和逐次实验，更多转向引导 Agent 与设定预算 |
| 领域判断 | 用硬件、编译和数值知识判断假设、异常和适用范围 |
| 结果验收 | 从检查代码，扩展到审查测试质量、测量条件、证据和风险 |

- 新手需要契约与验证引导；专家需要原始证据、参数控制和随时接管。
- 复杂探索和 Agent 无法推进时，开发者仍可直接编码和主导诊断。

**建议画面**：左侧“执行与操作”，右侧“定义、判断、验收”，以工作重心迁移表达，不画成能力完全替代。

## P7｜UX 变化：从工具与对话，走向可管理的任务体验

**页面要传达：人和 Agent 应共享同一任务上下文；用户始终知道目标、进展、证据和控制方式。**

| 体验问题 | 产品设计响应 |
|---|---|
| 要做什么？ | 从代码、错误或自然语言发起任务；呈现可编辑的目标、约束和验收条件 |
| 进行到哪里？ | 显示当前动作、进度、设备排队、预算和阻塞项 |
| 如何控制？ | 在授权范围内执行；支持暂停、取消、接管和调整预算 |
| 能否相信？ | 标明事实、推断与实测；从结论下钻到代码、测试与运行证据 |
| 如何继续？ | IDE、CLI、Studio 和 Agent 共享任务、运行与产物，支持恢复和交接 |

**建议画面**：任务工作台示意：顶部目标与状态，中部候选与时间线，侧边证据与控制。此图为设计方向，非已实现能力。

## P8｜UX 关键时刻：让开发者在需要判断时获得完整信息

**页面要传达：围绕启动、执行、审查和交付设计，而不只增加聊天入口。**

1. **启动任务**：展示目标、硬件、shape/dtype、精度、范围和预算；提示尚未确认的信息。
2. **执行与干预**：显示 Agent 的动作与失败原因；用户可暂停、修改边界或接管。
3. **审查候选**：对比 baseline 与候选的代码、正确性覆盖、测量条件、收益和波动；明确未覆盖项。
4. **验收与复用**：呈现是否满足目标、剩余风险和复现方式；用户决定接受或继续探索。

**建议画面**：四个连续界面状态，每个状态只保留一个用户决策和对应证据。

## P9｜场景示例：一次 RMSNorm 性能优化任务

**页面要传达：从目标设定到结果验收，展示三类变化如何同时发生。**

**任务设定**：指定设备及输入范围，保持接口和数值语义，最多尝试 20 个候选。此为虚构示例，不代表实测收益。

| 过程 | Agent 与工具 | 开发者与 UX |
|---|---|---|
| 建立基线 | 检索实现与测试；运行基线 | 开发者确认输入、容差和测量条件 |
| 搜索候选 | 提出分块等假设；编译并验证候选 | 用户查看进度、预算并可接管 |
| 对比验收 | 展示通过正确性检查的候选及性能分布 | 用户审查 Diff、覆盖和未测项，决定接受或继续验证 |

**建议画面**：三段式时间线，底部明确标出“人确认契约”“人决定验收”。

## P10｜落地方向：先让协作可控，再提升诊断与调优能力

**页面要传达：先建立可信的最小闭环，通过真实任务验证后逐步扩展。**

1. **受控执行闭环**：任务契约、结构化编译和测试、Diff、运行关联、暂停与接管。
2. **证据驱动诊断**：连接源码、编译和运行结果，展示失败原因与可复现信息。
3. **受预算约束的调优**：管理基线、候选与设备预算，确保正确性和测量条件可比。
4. **集成与团队复用**：补充模型级验证、结果包、审查记录与共享基线。

**验证方式**：用真实任务对照记录可信交付时间、人工介入、回归、复现率与设备成本；同时观察用户能否识别证据缺口并有效接管。暂不预设收益数值。

**建议画面**：四阶段路线图，底部放“效率、可信度、控制、成本”四类验证指标。
