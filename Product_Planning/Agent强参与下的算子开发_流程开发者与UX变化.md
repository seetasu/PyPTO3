# Agent 强参与下的算子开发：流程、开发者与产品体验变化

> 面向产品规划、体验设计与技术团队的讨论材料｜2026-10-27  
> 范围：PyPTO / PTO 等面向加速器的算子开发、验证、调优与集成。本文中的产品方向是设计推断，尚需结合真实任务验证。

## 一、核心观点

Agent 从回答问题、补全代码，向能够理解工程上下文、调用工具、修改实现并依据运行反馈持续迭代的参与者演进。算子开发的基本目标仍是交付语义正确、性能满足目标且能够集成的实现；变化在于，**大量中间操作可以由 Agent 组织，人更多地定义问题、约束探索、判断证据和承担交付责任**。

这带来三个相互关联的变化：

1. **任务流程：从人串联工具的线性步骤，变为围绕目标和证据的迭代闭环。** 编码、编译、验证、定位和调优可以在授权范围内反复执行；流程状态由任务、候选和运行记录承载。
2. **开发者：从主要执行者，转向任务定义者、领域判断者与结果验收者。** 手工编码仍然重要，但审查规格、验证策略、实验质量和取舍的比重上升。不同经验的开发者需要不同程度的引导与控制。
3. **产品体验：从提供独立工具和信息，转向支持人、Agent、Toolkit 共用上下文与证据的工作环境。** 产品既要方便人理解、干预和验收，也要让 Agent 能可靠调用工具、读取结构化结果并恢复任务。

这不是完全自动化的断言。自动化程度受语义清晰度、工具可靠性、硬件资源和组织治理约束；在复杂新算子、模糊需求和高风险集成场景，人仍可能主导实现和判断。

## 二、为什么需要重新设计

算子开发跨越数学语义、数据类型与精度、编译器、设备执行、硬件资源及模型集成。一个“能编译”的实现并不等于数值正确；一个特定输入上更快的 kernel，也不一定适合真实 workload 或提升端到端性能。Agent 能扩大探索速度，也可能放大错误规格、薄弱测试和不可靠测量的影响。

已有研究表明，执行和 profiling 反馈可以支持 kernel 的迭代改进；[KernelBench](https://arxiv.org/abs/2502.10517) 同时衡量正确性与相对基线的性能。[CUDA Agent](https://arxiv.org/abs/2602.24286) 研究将自动验证和 profiling 纳入 Agent 环境，并在其指定的 CUDA、硬件和 benchmark 条件下报告结果。这些结果不能直接推断为 PyPTO 或昇腾环境中的效果。另一项[研究](https://arxiv.org/abs/2609.21058)展示了测试容差和输出覆盖不足可能导致错误实现通过检查，也指出局部 kernel 收益不必然等于端到端收益。上述研究为设计方向提供线索，不代表本产品已验证的用户效果。

## 三、算子开发任务流程的变化

### 3.1 整体流程：从操作序列变为任务闭环

**以往的典型模式**：开发者理解需求 → 查资料和相似实现 → 编码 → 编译 → 修错 → 测试 → profiling → 手工修改、重复实验 → 集成。工具提供各步骤能力，由人携带上下文、决定下一步并拼接结果。

**Agent 强参与的模式**：人和 Agent 共同明确任务契约 → Agent 建立上下文和候选方案 → Toolkit 执行编译、验证和测量 → Agent 基于证据调整候选 → 人在关键取舍与验收处介入 → 固化结果。具体步骤可按失败和证据回退，不需要把流程强制做成固定向导。

```text
任务目标与约束 ─→ 上下文与计划 ─→ 候选实现 ─→ 编译 / 正确性 / 性能 / 集成验证
      ↑                                  │                     │
      └──── 人修订目标或约束 ← 审查与决策 ← 证据、失败与下一步 ←┘
```

### 3.2 各阶段具体变化

| 阶段 | 传统工作重心 | Agent 强参与后的变化 | 人的关键判断与阶段产物 |
|---|---|---|---|
| 定义任务 | 人理解需求并自行决定实现路径 | Agent 将自然语言整理为契约，发现缺失条件，关联已有实现 | 人确认数学语义、shape/dtype、精度、目标硬件、性能目标、范围与预算；产出任务契约 |
| 理解上下文 | 人查源码、文档、环境和历史记录 | Agent 跨源码、API、测试、编译配置与历史 Run 检索，提供可回链的摘要 | 人确认领域假设和适用范围；产出上下文与未知项 |
| 实现与编译 | 人编写代码，逐条处理诊断 | Agent 生成或修改候选，调用编译与静态检查并迭代 | 人处理语义歧义与重要设计取舍；产出 Diff、编译结果和失败记录 |
| 正确性与调试 | 人构造测试、观察错误、跨层定位 | Agent 扩展测试、比较 reference、追踪首个分歧并提出修复假设 | 人确认 oracle、容差与覆盖是否足够；产出测试覆盖、数值证据及未解决风险 |
| 性能调优 | 人观察 profile，逐个调整参数并记录 | Agent 在受限预算内提出候选并组织实验；工具采集指标和资源信息 | 人确定收益与精度、资源、适用范围的取舍；产出可比较的候选和测量结果 |
| 集成与交付 | 人移植实现、验证模型效果和回归 | Agent 协助检查接口、集成与回归，汇总候选及证据 | 人决定是否纳入基线；产出可复现结果、变更和已知限制 |

**门禁保持独立**：编译通过、正确性通过、性能达标、集成通过分别表述；某一项成功不能替代其他项。测试覆盖不足时标明“已通过哪些检查”，不能宣称普遍正确。性能对比应记录输入、设备、版本、预热、重复次数及波动；不同条件不直接排名。

### 3.3 新增的工作与风险

- **任务契约和授权**：将不可变语义、允许修改范围、设备时间、实验次数、停止条件写清楚；需要区分可自动执行的工作区操作与有成本或外部影响的操作。
- **实验治理**：同一任务可能产生多个候选和多次运行，必须关联源码版本、参数、环境、结果和失败原因，避免选错候选或把历史结果当作当前结果。
- **验证策略本身的审查**：不能只让生成实现的 Agent 证明自己正确。需要独立参考实现或已知可信基线、边界与异常用例，并审查容差和输出覆盖。
- **恢复与交接**：设备排队、长任务中断或上下文切换后，任务应能从已保存的状态继续，另一位开发者也能理解进展。

## 四、开发者有哪些变化

### 4.1 工作重心与能力要求

| 维度 | 工作重心的变化 | 产品应支持 |
|---|---|---|
| 问题定义 | 从描述“怎么做”更多转向说明“什么结果可接受”，包括语义、边界和资源 | 任务模板、缺失条件提示、可编辑契约 |
| 领域知识 | 硬件、编译、数值和模型知识仍用于判断方案与异常；记忆 API 和手工串命令的负担可能下降 | 按需解释、源码与硬件证据联动、领域知识引用 |
| 验证与审查 | 从逐行构造实现扩展为审查 Diff、测试质量、实验条件与结论适用范围 | 门禁与覆盖摘要、结论到证据的下钻、复现入口 |
| 实验组织 | 从手动执行单次尝试转向规划搜索空间、预算和停止条件 | 候选对比、排队和成本、失败归因、暂停与恢复 |
| 协作与责任 | Agent 可承担部分执行，人仍需对业务语义、接受风险和交付结果负责 | 任务级控制、重要决策记录、团队可共享的结果包 |

这是工作重心的预期变化，不意味着每位开发者都应成为相同的“Agent 管理者”。简单问题可以由人直接编辑；语义探索、低层性能瓶颈或 Agent 反复失败时，专家可能重新主导诊断和实现。

### 4.2 不同用户的需求

- **新手或跨领域开发者**：需要理解术语、获得契约与验证引导，尤其要知道哪些约束仍未确认；风险是过度相信表面上合理的解释。
- **经验丰富的算子/性能工程师**：需要快速控制搜索范围、查看原始 trace、覆盖 Agent 假设并自行编辑；风险是摘要掩盖关键细节或自动实验消耗设备资源。
- **集成与模型工程师**：关注目标 shape 的覆盖、接口兼容、模型级收益与回归，不一定需要先理解所有底层实现；需要从模型结果下钻到相关算子。
- **团队负责人或评审者**：关注可复现性、风险、资源投入和交付状态，需要跨任务查看决策与证据，而不是阅读完整聊天记录。

以上是待访谈验证的用户分层；一个人可能在不同任务中切换角色。

## 五、产品 UX 体验设计有哪些变化

### 5.1 设计对象与原则

产品需要同时服务**人类用户**与**Agent 这一工具使用者**。前者需要理解、判断与控制，后者需要明确的工具契约、稳定结果和可恢复的上下文。两者应共享同一事实来源，而非分别维护无法对齐的状态。

| 体验维度 | 设计转向 | 具体体验 |
|---|---|---|
| 入口 | 从选择工具入口到表达任务意图 | 自然语言结合结构化目标、输入输出、约束与验收；可从源码、报错、Run 或模型入口带上下文发起 |
| 工作状态 | 从对话记录到可持续的任务状态 | 展示目标、当前阶段、正在执行的动作、预算、阻塞项和下一步；支持暂停、取消、恢复和接管 |
| 信任 | 从听结论到检查证据 | 区分源码事实、推断、编译结果与设备实测；结论可下钻至 Diff、日志、Tensor、IR、trace 和原始数据 |
| 控制 | 从每一步都操作到按风险和预算委托 | 清晰展示当前范围和可自动执行动作；需要决策时提供影响、成本与可选项，允许修改边界 |
| 审查 | 从阅读大量日志到围绕决策组织信息 | 默认呈现目标是否满足、候选变化、各门禁、对比条件、未覆盖风险；保留专家下钻路径 |
| 跨工具 | 从重复提供上下文到任务连续 | IDE、CLI、Studio 和 Agent 共享任务、运行标识与产物；入口切换后继续同一工作 |
| Agent 工具体验 | 从人类可读日志到可组合的执行能力 | CLI/API/MCP 等按实际能力提供稳定输入输出、错误类型、超时、成本与副作用描述；结构化结果关联原始产物 |

**建议的信息层次**：第一层回答“目标、进展、是否需要我”；第二层回答“候选、验证、收益、风险”；第三层进入源码、IR、Tensor 和 profiling 细节。详细轨迹可查，但不应要求用户逐条阅读才能完成判断。

### 5.2 关键交互时刻

1. **任务启动**：Agent 先展示可编辑的任务摘要，标出缺失的语义、目标硬件和验收条件；可从已有工程自动填充，但区分推断与已确认信息。
2. **自主执行中**：时间线展示正在做什么、已完成什么、设备排队和剩余预算；可暂停或接管。错误应说明失败阶段、证据和下一步，不只输出一段日志。
3. **需要人决策**：在精度与性能取舍、扩大范围或超预算等节点，展示候选、影响和所需决定；日常已授权操作不反复打断。
4. **候选审查**：并列展示 baseline 和 candidate 的代码变化、正确性覆盖、测量条件、收益及波动；不合格候选保留原因，不进入合格排名。
5. **交付与复用**：生成关联任务契约、源码版本、运行环境、命令、证据和未覆盖项的结果包；用户可复跑、继续探索或明确接受。

### 5.3 支撑体验的共享对象

建议以 `Task → Candidate → Run → Evidence → Decision` 组织工作：Task 保存目标、范围与预算；Candidate 关联实现和 Diff；Run 固定实际代码、环境、输入和配置；Evidence 连接诊断、测试和测量产物；Decision 保存人的取舍。一个候选可有多次运行，证据须指向实际运行版本。该模型是产品建议，不预设当前系统已具备这些对象。

## 六、示例：优化一个 RMSNorm 算子

**任务**：在指定设备和输入集合上降低延迟，保持接口和已有数值语义；最多尝试 20 个候选，设备运行预算由开发者设定。该例为虚构场景，不代表实测收益。

1. Agent 读取实现、测试与已有运行，列出输入 shape、dtype、容差、目标设备和缺失的基线条件，开发者补全并确认。
2. Toolkit 运行基线，记录代码版本、设备、输入、预热和重复测量；Agent 根据 profile 提出分块或流水参数假设，给出搜索范围。
3. Agent 生成候选并依次调用编译、正确性和性能检查。失败候选记录错误和原因；通过正确性检查的候选才参与性能比较。
4. 界面显示各候选的 Diff、覆盖用例、延迟分布和资源消耗。若最快候选仅覆盖部分 shape，明确标出适用范围与未测项。
5. 开发者检查测试与证据，决定接受候选、补充模型级验证或继续探索；工具保存复现信息和决策。

该案例中，Agent 减少了操作和实验编排，人仍决定任务语义、验证充分性和最终取舍。

## 七、落地优先级与验证

| 阶段 | 优先能力 | 验证问题 |
|---|---|---|
| 先建立受控闭环 | 任务契约、结构化编译/测试工具、Diff、Run 关联、进度与停止控制 | 开发者能否理解 Agent 做了什么，并在失败后接管？ |
| 再强化证据驱动诊断 | 跨源码/编译/运行的关联、首个数值分歧、错误与复现信息 | 能否更快定位问题，同时减少缺乏证据的修复？ |
| 再扩展性能探索 | 基线管理、预算、候选隔离、正确性门禁和可比性检查 | 在相同设备和预算下，是否获得可复现收益且不增加回归？ |
| 最后连接集成与团队 | 模型级验证、结果包、审查和共享基线 | 算子收益是否对真实 workload 有价值，团队能否复用结果？ |

建议通过已有真实任务做对照试验，按任务复杂度、用户经验与硬件资源分组，记录从提出任务到可信交付的时间、人工介入次数、正确性覆盖、误改/回归、复现成功率、设备时间和人对候选的接受原因。指标需同时报告失败、未完成任务和成本，避免只统计成功案例；体验研究应观察开发者是否能识别证据缺口、及时停止和有效接管。
