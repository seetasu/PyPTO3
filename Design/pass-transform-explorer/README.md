# Pass Transform Explorer

把 PyPTO 编译器从「输入算子、输出二进制的黑盒」变成一条可以逐站检查的流水线。

工具直接解析 `Data/**/passes_dump/*.py`——每个 Pass 执行后的真实 IR 快照。

左栏顶部切换两条**正交主线**，它们看的是同一批快照，只是主角不同：

### 按 Pass（横向）——「这个 Pass 做了什么」

| 问题 | 视图 |
| --- | --- |
| 变化发生在哪个 Pass？ | **Pass 时间线**：按实际改动行数排序，空操作 Pass 直接置灰 |
| 具体改了哪几行？ | **代码 Diff**：按函数拆分，token 级高亮，并排 / 统一双模式 |
| 这个 Pass 到底优化了什么？ | **变化概览**：从 AST 实测出的结构增量 + **结构图**：五种视角的前后对照 |

### 按 Callable（纵向）——「这个算子经历了什么」

选定一个 callable，看它穿过全部 Pass 的一生。索引是 `pass.functions` / `pass.changedFunctions`
的转置，不引入任何新事实；左右两区直接复用 Pass 主线的结构图与 Diff，只是锁定到这个 callable。

页面分三区，点历程条上任意一步，左右两区同时跟随：

| 区域 | 内容 |
| --- | --- |
| **顶部** | **成果条** + **历程条**：只列真正改动过它的 Pass，每步一句话说清做了什么 |
| **左下** | **这个 Pass 做了什么**：该 Pass 的推荐视角，锁定在这个 callable 上 |
| **右下** | **代码怎么变的**：该 Pass 对这个 callable 的 token 级 Diff |

**行数不是语义。** 一个 Pass 让函数长了 50 行，这只说明体积，不说明它做了什么优化。
历程条的主徽章因此用索引里现成的**结构计数器**——tile 分配、循环、任务——它们才说明
Pass 做了什么：`AutoTileMatmulL0` 加循环是因为它把 matmul 分块，`MemoryReuse` 减分配是因为
它让缓冲区共享存储。语句数保留但降级为次徽章，并在结构计数器已经解释了这一步时直接隐去。
两个计数器都没动、但 IR 确实被改写的 Pass（填地址、改名、重排）标成「就地改写 N 行」，
具体改了什么交给下面两区。

以 `#l3_decode_csa/c/qk_pv/35` 为例，16 个 Pass 改动过它：

```text
09 OutlineIncoreScopes     循环 +5           外提为独立函数
17 AutoTileMatmulL0        循环 +2           matmul 分块
23 ExpandMixedKernel       循环 +2           InCore → AIC+AIV+Group
25 SplitVectorKernel       循环 +3
28 SkewCrossCorePipeline   循环 +2           跨核流水错位
33 InitMemRef              tile 分配 +53     建 MemRef
35 MemoryReuse             tile 分配 −41     缓冲复用
36 AllocateMemoryAddr      就地改写 190 行   只填地址，不改容量
46 Simplify                循环 −1
```

选中 `MemoryReuse` 时，左下的内存视图给出这一步的实际收益：**合计 274 KiB → 49 KiB，
缓冲 30 → 5 个**。顶部成果条给出全程：**tile 分配峰值 53、终值 12，最终省下 41**。

### 控制流与数据流

这两个视角原本共用一个渲染器：同样的 176×40 圆角框、同样的左右分层贝塞尔边，只有副标题
文字不同。于是"嵌套结构"和"值依赖"看上去是同一张图——数据其实完全不同，只是没画出来。

`controlTree` 产出的是**树**（严格父子、节点类型 `fn`/`for`/`if`/`else`/`with`/`block`），
`dataflowGraph` 产出的是 **DAG**（多对多 def-use、节点带 `op`/`shape`/`dtype`/`space`）。
两者现在各画各的：

| | 控制流 | 数据流 |
| --- | --- | --- |
| 形式 | 缩进树（HTML 行 + 缩进导轨） | 分层 DAG（SVG） |
| 读什么 | 嵌套有多深、循环跑多少次 | 谁产生、谁消费、值有多大 |
| 节点 | 按类型给字形：`⟳` 循环 / `◆` 分支 / `◇` else / `▪` 语句块 | 参数是虚线胶囊（源），值是方块 |
| 着色 | 循环蓝、分支橙 | 填色 = 片上内存（Mat / Vec / Acc，与语义下降图同一套） |
| 边 | 不画——用缩进表示包含 | 粗细 ∝ 流过的字节数 |

控制流独有的量是**循环倍数**：`pipeline(2)` 和 `range(128)` 在原来的图里都只是一个框，
现在分别带 `×2` 和 `×128` 徽章，语句块还会累乘外层循环给出实际执行次数。
qk_pv 顶部因此直接写着「5 个循环 · 最深嵌套 7 · 最内层执行 ×128」——这是 DAG 画不出来的。

数据流独有的量是**字节**。标签也调了主次：原来首行是 `qk_bias_row_inline2419__ssa_v0`
（SSA 噪声），现在首行是算子 `t.slice`，值名和 `[1×128] FP32` 退到副行。

#### 结构图不再被裁掉

结构图的 SVG 原本按**内容尺寸**生成（比如 2048×776），放在一个 `overflow:hidden`、
高度只有 420px 的容器里。pan/zoom 移动的是 SVG **内部**的 `<g>`，所以一拖，节点就越过
SVG 自己的边界被裁掉 —— 断在节点中间，下面露出容器的点阵底纹。看起来像内容区被截断，
其实是被一条看不见的内部边界切掉了。

而且没有任何适应窗口的动作：一张 1926×759 的图在 810×652 的面板里打开，只看得到左上角。

改法：

- SVG 改为**填满容器**（`100% × 100%`），它的裁剪区域从此就等于你看得见的区域。
- 打开时自动缩放到能看见整张图，右下角给「适应 / 1:1 / 当前缩放」三件套。
- 拖拽有边界约束，任何方向都至少留 80px 内容在屏幕上，不会一甩就空白。

三个容易漏的细节：

1. **按墨迹算，不按画布算。** 布局在 `box` 里留了边距，按 box 留 80px，实际只剩 43px 内容。
   现在 fit 和 clamp 都用 `getBBox()` 的真实内容范围。
2. **容器可能是 0×0。** 面板折叠或布局未稳时 fit 会静默失效。加了 `ResizeObserver`，
   在容器第一次有真实尺寸时补一次 fit（读者一旦动过就不再插手）。
3. **适应得真的能适应。** 数据流图有 18959×7497，滚轮下限 12% 根本装不下。
   现在显式 fit 允许到 3%，滚轮下限仍是 12%；且滚轮下限会跟随 fit —— 否则在 4% 时
   随便滚一格就会跳回 12%，视野瞬间放大三倍。

#### 函数体去了哪里

`InlineFunctions` 的变化概览原本是一串列表：「移除 20 个」，外加二十行函数名。
看得到数量，看不到**哪段代码去了哪里**。现在它先给一张迁移图。

左列一行一个函体，行内条长 = 语句数，所以 `hc_pre` 的 193 条和 `rms_norm` 的 10 条一眼分得开；
条带把这份重量牵到右边的接收方，被复制到多处的函体会分叉并标 `×N`——
复制正是内联的全部代价，画成一根线就把它藏了。点任一方块直接跳到那段代码的 diff。

##### 同一张图服务三种方向，因为它们本来就是一回事

| 方向 | 代表 Pass | 图里是什么 |
| --- | --- | --- |
| 溶解 | `InlineFunctions` | 20 个函体 → 3 个接收方 |
| 外提 | `OutlineIncoreScopes`、`ExpandMixedKernel` | 60 个新函数 ← 它们原来所在的函数 |
| 套壳 | `OutlineClusterScopes` | **没有图**，因为什么都没搬 |

第三种是这个功能最该说清楚的地方。`OutlineClusterScopes` 新建 48 个函数，按「外提」去画，
会写成「109 条语句从 decode_csa_test 提了出去」——而那个函数这一步实际**涨了 3 条**，
48 个新函数全是 1～4 条语句的 SPMD 壳，包着原地没动的函体。

区分它们的判据是结构性的：**新函数如果调用了一个 Pass 前就存在的名字，它是壳，不是被提出来的函体**。
在真实 dump 上这条判据把 `OutlineClusterScopes` 切成 48/48 全是壳、`OutlineIncoreScopes` 切成 60/60 全是真外提，
中间没有含糊的。

##### 行号属于哪个文件，必须说清楚

Diff 的两列行号分别来自两份 dump 文件本身（`decoLine` 起算），不是函数内的相对行号：

```text
点 hc_pre（第 01 步）  左列 273  = 00_frontend.py 第 273 行（@pl.function 那行）
                        右列 空    = 它在 Pass 后已经不存在
点 decode_csa_test      左列 1772 = 00_frontend.py 第 1772 行
                        右列 221  = 01_after_InlineFunctions.py 第 221 行
```

跳转原本只按数字在所有行号格子里找第一个匹配。但每行渲染**两列**行号、前列在先，
而一个跳转目标只属于其中一个文件——于是 after 文件的目标会被一条碰巧同号的 before 行截胡。

这不是理论风险：9 个 host 目标里有 2 个满足碰撞条件，其中第 09 步的 `decode_csa_test`
真的会跳错——它的 after 行 2408 落在 before 区间 [204, 2529] 内，而 after 的 2408 行
因为落在未改动区被折叠、**根本没渲染**，所以点击会高亮到 4434 个格子以外一条毫不相干的行。

现在每个可点目标都带 `data-side`（被溶解的函体 = before，被外提的 = after，幸存的 host = after），
跳转只在对应那一列里找。目标行如果被折叠在未改动区，就如实提示
「Pass 后第 2408 行不在本 Pass 的变更范围内」，而不是乱高亮一行。

##### 图里的每个数都要能和隔壁卡片对上

第一版这里翻了两次车，都是读者一眼就会发现的那种：

**「21 个函体」和隔壁「移除 20 个」对不上。** 内部结构是一行一个「函体×接收方」，
`merge2_top512_pairs` 进了两个调用方就成了两行，于是数行数得到 21。
现在左列一行一个**函数**，一个函体有多个去处就从同一行分出多条带子，计数回到 20，
并且明写「和上面『函数结构』的移除数一致」。

**三个接收方只看得见一个。** 方块高度按归因权重分配、但有最小高度兜底，
两者相加会超出预先算好的画布高度，后两个方块被画到了 SVG 外面裁掉了 —— 看起来就像
「21 个函数变成了 1 个」。现在先排完方块再按实际占用定画布高度。

还有一处没等人来问就先堵上：右侧各方块的「收下」相加是 21，仍然比 20 多一个，
因为跨去处的函体被两边各记了一次。这正是读者会做的第一步算术，所以图里直接写出来，
而不是留两个都对的数字看起来像矛盾。

##### 归因和实测并排放，因为它们不相等

「谁的函体进了谁」是从调用图推出来的，不是文本比对。每个接收方同时显示两个数：
归因（调用图推出的语句数）和实测（两份快照的语句差）。它们差几个百分点——
内联会吃掉调用语句本身，还会折掉一些常量——把其中一个单独拿出来当结论，就是拿估计冒充测量。

```text
decode_csa_test          语句 1 → 1,600     归因 1,627 · 实测 1,599（差 +2%）
indexer_topk_query_merge 语句 31 → 83       归因    60 · 实测    52（差 +15%）
```

##### 为此修了一个真 bug：尾调用不算调用

`return self.decode_csa(...)` 这种写法，解析后只留下原始字符串，没有表达式树，
于是**调用图完全看不到它**。94 份快照里只有 1 条这样的边——但它正好承载了
`InlineFunctions` 搬动的 1,647 条语句里的 1,599 条，第一版迁移图给最大的接收方算出来 0。

修在解析器：返回值和别处的值一样是表达式。顺带也补上了**调用/作用域视角**一直缺的这条边。

#### 控制流和内存归属：两条并排的条，不是四个数字

`range 85 → 88` 是四个数字，要读者自己做减法，而且看不出形态。
现在每一行是 Pass 前 / Pass 后两条并排的条：

- **共用一把标尺**，所以行与行之间可比。`LowerPipelineLoops` 那一步，
  Vec 的 1,328 → 1,834 和 Left 的 31 → 93 放在同一把尺上，
  能看出 Left 翻了三倍但它本来就很小——各自归一化的话这个判断就没了。
- **最大嵌套深度**不用条，用梯级：它是个计数，但本质是形状。新增的那一层单独着色。

#### Pass 按性能影响分档，真实 perf hint 挂到对应 Pass 上

时间线上原本只有 IR 体积一个维度，`FlattenCallExpr`（+460 行的纯形式变换）和 `CanonicalizeIOOrder`
（0 行改动，却决定 MTE 能不能跑在计算前面）看起来一模一样。现在每行 Pass 左缘有一条分档色带。

| 档 | 依据 | 判据 | l3 / fwd 条数 |
| --- | --- | --- | --- |
| 性能决策点 | **事实** | 全 PyPTO 只有这三个 Pass 注册了自己的性能提示码（`PH-MR-*` / `PH-AT-*` / `PH-DSA-*`） | 3 / 3 |
| 调度与落位成形 | 文档推断 | 决定指令顺序、核间重叠或片上落位，且没有自检 | 11 / 9 |
| 搬运与指令量 | 文档推断 | 改变搬多少字节、发多少条指令 | 13 / 9 |
| 形式变换 | 其余 | 收敛写法，不搬动工作量 | 25 / 21 |

分档强度不一样，所以卡片上明写「依据：事实 / 文档推断」，每条都带出处文件名。
`form` 一档**不给任何标记**——没标记要读作「这里没什么可说的」，而不是「已验证中性」。

##### 分档和实测是两件事，界面上从不合并

色带是关于这个 Pass 的**常驻属性**；条数徽标是**本次编译真实发生过什么**，读自该次运行自己的
`report/perf_hints.log`。两者分开，才说得清这个对比：

```text
l3_decode_csa    MemoryReuse  [性能决策点]  ⚠ 33   ← 33 次双缓冲降级，全是 "stages … serialize"
decode_fwd_layers MemoryReuse [性能决策点]         ← 同一个 Pass，同一档，这次一条没报
```

所以高档位 + 没徽标不是「没数据」，卡片会把话说完：决策档有专属提示码，不报就是判定都满足了；
成形档本来就没有自检，成形得好不好不会有任何信号。

##### 197 条提示不属于任何 Pass

l3 那 230 条里有 197 条来自 `TileInnermostDimGranularity`——流水线跑完之后的校验器，不是 Pass。
把它挂到任何一个 Pass 下都是误导，所以它单独立在第 00 步（前端 IR）下，标题直接写「不是 Pass」：
沿时间线找不到是哪一步引起的，因为答案是源码里的 tile 形状。

归属不靠猜。日志每行自带 emitter 名（`[perf_hint PH-MR-001] MemoryReuse: …`），
build 拿它跟本次运行的 Pass 名集合比对，命中就归到那个 Pass，没命中就进「非 Pass」桶——
不需要任何硬编码的校验器名单。230 行全部解析成功，0 行落空。

##### 两处自己踩的坑

档位最初是名字旁边的文字小标签，实测吃掉 160px 名字列里的 32–55px，被截断的 Pass 名从 3 个涨到 9 个。
档位本来就只有四取一，不需要在行内占字：改成左缘色带后回到 3 个，而且色带自成一列，更好扫。

日志里的路径带编译机的绝对前缀和用户名。写进 `data/index.js` 前统一裁到仓库相对段
（`pypto-lib/models/…/decode_o_proj.py:556`），有用的部分一点没少。

#### 视角页签会按当前 Pass 开关

一个视角要看的东西，在流水线前段往往还不存在：`InitMemRef` 之前没有 MemRef，纯计算核里没有任务。
这些页签以前照常可点，点进去是一张空图。现在它们会置灰、拒绝点击，并在 hover 时说明原因。

能不能点由**真实快照**决定（`lensHasContent` 跑在已加载的前后两份 IR 上）；
"要到第几步才有"则读索引里逐 Pass、逐函数的 `loops` / `allocs` / `tasks` 计数。
两者分开，是因为索引**没有 buffer 计数**，而内存类视角是认 buffer 的：

| 视角 | 索引字段 | 与判定是否等价 | 提示措辞 |
| --- | --- | --- | --- |
| 控制流 | `loops` | 等价 | 可以断言"该函数整条流水线上都没有" |
| 任务 DAG | `tasks` | 等价 | 同上 |
| 内存布局 / 缓冲生命期 | `allocs` | **不等价**（漏掉只有 memref、没有 alloc 的函数） | 只说"缓冲由第 33 步 InitMemRef 引入"，不对本函数下断言 |

这个区分不是洁癖：`decode_csa_test` 的 `allocs` 全程为 0，但它在第 33 步之后是有 buffer 的。
按 `allocs` 措辞会写出"它整条流水线上都没有缓冲"——一句假话。

配套行为：

- 用不了的页签用 `aria-disabled` 而不是 `disabled`。`disabled` 的按钮收不到鼠标事件，原生 tooltip 不会弹，
  而这里提示正是重点；点击由脚本拒绝并 toast 同一句话。
- 读者显式选过的视角记在 `state.lensWanted`：沿时间线走到它失效的 Pass 会临时回退，
  走到重新可用的 Pass 会自动回到它。
- 程序级视角（调用 / 作用域）在函数级逻辑之前就 return 了，所以那条路径要单独调一次开关判定，
  且当 `state.fn` 在该快照里不存在时不做判定——宁可全开，也不要全关。

核对方式是拿页签状态和快照真实内容逐项比对：14 个 Pass × 4 个受限视角 = **48 项判定，0 处不符**。

#### 前后变化可以放出来看

并集图只布一次版，所以一个节点在 Pass 前后**不会移动**——这正好让变化可以就地播放，
而不是靠四种颜色一次性摊开。播放条分五个阶段，每个阶段是 diff 的一个类别：

| 阶段 | 画面 |
| --- | --- |
| 0 之前 | 新增的还不存在；改写的节点显示**旧的算子与类型** |
| 1 退场 | 只有将被删除的节点和边保持全亮，其余压到 18% |
| 2 改写 | 删除的已消失；改写节点亮起，文字换成新的算子与类型 |
| 3 新增 | 新增的节点和边亮起 |
| 4 之后 | Pass 执行后的完整形态 |

每个阶段都是一个**静态状态**，动画来自状态之间的 CSS 过渡（420ms），不是逐帧 JS——
qk_pv 这一步有 182 个节点、339 条边，逐帧驱动会掉帧。`prefers-reduced-motion` 下过渡自动关闭。

改写节点同时带着新旧两份文字（`.is-was` / `.is-now`），靠阶段切换显隐，
所以「`t.slice` 变成了 `T.load`」这种事实是直接读出来的，不用去比对两张图。

实现上有两个坑值得记一笔：

- `:not()` 会带上参数的特异性，所以「变暗」规则（`.ptx-node:not(.ptx-node--del)`）
  原本压过了「尚未出现 / 已经消失」规则，导致阶段 1 的新增节点显示成 18% 而不是不存在。
  修法是把隐藏规则写成双类名并排在变暗规则之后。
- 除数据流外的视角都在 `drawGraph` 之前就 return 了，所以停止播放必须放在视角分发的入口，
  否则切走之后定时器还在对着已经不存在的画布跑。

#### 连线走正交折线

分层布局在层与层之间留下空走廊，所以边不走直线，改走走廊：出源点 → 竖直走廊 → 水平车道 → 进目标点，
拐角圆角化。跨多层的边会先算出中间各层节点的 y 占用区间，合并后挑一条空车道穿过去。

改之前用的是直接连两端的三次贝塞尔：qk_pv 的数据流图 339 条边里 **147 条（43.4%）从节点框里穿过去**。
改之后 0 条。全量核对（5 个 Pass × 5 个视角、3925 条边）同样是 0 条穿框、0 条非法路径。

#### 任务 DAG 和数据流的关系

同一段程序的两个层级，不是同一张图的两种画法：

| | 数据流 | 任务 DAG |
| --- | --- | --- |
| 节点 | 每个 SSA 赋值 + 每个参数 | 每个 `pl.at` 作用域 / `pl.submit` / `pl.spmd_submit` |
| 边从哪来 | **推导**：扫右侧表达式引用了哪些名字 | **声明**：`deps=` 关键字里写明的 TASK_ID |
| 说明什么 | 数据上谁必须先于谁 | 运行时被告知要等谁 |
| 作用域 | 每个函数都有 | 只有宿主函数有（116 个函数里 1 个） |

以 `decode_csa_test` 为例：

```text
Pass 08   14 个任务（全是 pl.at 作用域）· 1 条依赖边   ↔  数据流 601 节点 / 744 边
Pass 11   53 个任务（spmd 41 + submit 12）· 25 条依赖边 ↔  数据流 444 节点 / 761 边
```

粒度差约一个数量级：一个任务节点内部往往是几十个数据流节点。两者可以不一致，而不一致正是有价值的地方——
任务边多于数据依赖 = 过度同步，白白丢掉并行；数据依赖跨了任务边界却没有对应任务边 = 依赖漏写。
本 demo 目前只是分别画出来，还没做交叉比对。

### Pass 专属图

通用视角只能说「IR 变了」。读者想知道的是**这一类 Pass 在做什么**——外提是把一段区域抬成函数、
必须定下边界；下降是把 tensor 语义里隐含的搬运写成显式指令。这是两张完全不同的图，所以按 Pass
类型各画各的，排在视角条最左、默认推荐。

| Pass | 专属图 | 画什么 |
| --- | --- | --- |
| `Outline*Scopes` | **外提** | 宿主区域 → 独立函数 + 一次调用；逐个列出跨边界的值 |
| `ConvertTensorToTileOps` | **语义下降** | 值落到哪块片上内存（Vec / Mat / Acc），以及为此插入的 load / store |

**外提图**画的就是那道切口：区域原本随手引用上下文，外提后每个值都得在边界上点名。
所以图里一个值一根线，线的方向就是它的去向。方向不能只看一处——

- 参数上的 `pl.Out` / `pl.InOut` 包装给出声明的方向；
- 函数体末尾的 `return` 给出实际带回去的值；
- 函数体里对入参**同名基**的重新定义（IR 此时仍是函数式的，更新表现为新的 SSA 版本）。

三者合起来才是真相。一个跨迭代累加器是以普通 `in` 参数进去、从 `return` 出来的，
单看任何一处都会漏掉。据此分出五种跨界方式：

| 方向 | 判定 | 含义 |
| --- | --- | --- |
| 进 + 出 | `in` 参数且出现在 `return` | 循环携带的累加状态 |
| 原地改写 | `pl.InOut` | 直接写回调用方的缓冲 |
| 只出 | `pl.Out` 或只在 `return` 里 | 新产出的结果 |
| 改了没出去 | 体内重定义，但无 Out/InOut、也不在 `return` | 签名上没有出口，只能靠内存副作用 |
| 只进 | 其余 | 只读输入 |

每个 callable 的判定都不一样，顶部那句结论也就不一样：

```text
qk_pv                14 个跨界值 · 进+出 3    l / m / o，online softmax 的累加器
comb_sinkhorn         7 个        · 原地改写 1 + 只出 1
qproj_matmul          6 个        · 进+出 1    入口静态体积 32 MiB（wq_b 是 INT8 权重）
kv_touch              1 个        · 原地改写 1  3 条语句，纯副作用
csa_cache_writeback   3 个        · 改了没出去 1 调用处没接返回值，靠内存副作用生效
tp_o_rs_wait          2 个        · 全只读      DistributedTensor 上的同步等待
```

图按**面板实际宽度**排版（callable 模式下这一栏约 370px），不画宽了再交给浏览器缩——
缩到 0.44 倍时 12px 的标签只剩 5px 高，比没有图更糟。

**语义下降图**画的是**落位**。tensor 域里一个值只有形状和 dtype；tile 域里它必须住在某块
具体的片上内存上，而把它搬过去的指令也得写出来。落位就是这个 Pass 的产物——顺带还告诉你
这是个什么核：

```text
qk_pv          落位 0 → 54   Mat 31 · Vec 19 · Acc 4   三块都用上，矩阵和向量混在一个核里
qproj_matmul   落位 0 → 12   Mat 4 · Acc 8             操作数进矩阵区、结果落累加器，典型 matmul
rms_norm       落位 23 → 45  Vec 45                    全在向量区，纯向量 kernel
tp_o_rs_wait   无落位                                   同步等待，没有数据要放
```

数据取自分析器已经算好的 `memSpaces` / `valueKinds`，不是现场正则。搬运方向则从
`pl.tile.load(..., target_memory=pl.Mem.X)` 里直接读出来，`tile.store` 一律回 GM，
所以图上 GM → 各内存区的 load 计数和回写的 store 计数都是实数。

> 这里原来画的是两条算子流的序列比对（一条对齐后的色块条）。它在 640px 画布上尚可，但
> callable 模式下这一栏只有 ~358px，103 个单元格每个宽 5px、没有任何标签——读不出信息，
> 已替换。归一化算子名的那套逻辑保留在"新出现的指令"一行里：`pl.tensor.exp` 与
> `pl.tile.exp` 都归到 `exp`，否则 `tile.gather_row` 会被误报成新增搬运。

判断「新出现」也要用归一化名——否则 `tile.gather_row` 会被误报成新增搬运，而它在 tensor 域
本来就有，只是换了域。

没有专属图的 Pass 不显示这个视角，落到下面两个差分视角。

### 两个差分视角

原有的五种结构视角回答「这份 IR 长什么样」，其中两种是 **program 作用域**——在 callable 视图里，
不管选哪个 callable 都渲染出字节级相同的一张全程序图。所以这里补了两个**差分且函数作用域**的视角，
它们回答的是「这一步对**这个** callable 做了什么」：

| 视角 | 回答 | 适合 |
| --- | --- | --- |
| **算子迁移** | 退掉了哪些算子、换上了哪些，同名的左右配对 | 下降类（`Convert*` / `Lower*` / `Legalize*`） |
| **缓冲生命期** | 每个缓冲的存活区间画成一条横条，横轴是语句序号 | 内存类（`InitMemRef` / `MemoryReuse` / `AllocateMemoryAddr`） |

**算子迁移**把直方图增量变成一句话。`ConvertTensorToTileOps` 对 `qk_pv` 不是「多了 6 行」，而是：

```text
pl.tensor.gather_row  9  ⟶  pl.tile.gather_row  9
pl.tensor.slice       8  ⟶  pl.tile.slice       6
pl.tensor.matmul      2  ⟶  pl.tile.matmul      2
pl.tensor.exp / row_max / row_sum / cast …  ⟶  tile 同名
未配对新增：pl.tile.store 0→9、pl.tile.load 0→2   （tensor 域里隐含的搬运，现在显式了）
未配对移除：pl.tensor.assemble 7→0
```

**缓冲生命期**把「复用」画成字面意思。复用不是「缓冲变少了」，而是**一个缓冲活得更久、替多个短命
缓冲干活**。所以每个缓冲画一条横条，`MemoryReuse` 之后许多短条并成少数长条，被拉长的那几条高亮：

```text
qk_pv          40 → 15 个缓冲   274 KiB →  49 KiB    4 条被拉长
hc_post       156 → 12 个缓冲  2.32 MiB →  96 KiB
kv_proj_matmul 23 → 13 个缓冲   440 KiB → 232 KiB
```

推荐视角按 Pass 自动选：有专属图的 → 专属图；内存阶段 → 缓冲生命期；原本推荐调用图或数据流的 → 算子迁移；
控制流与任务 DAG 保持不变。**如果自动选中的视角在这一步没有数据**（`InitMemRef` 之前没有缓冲、
计算 kernel 里没有 task），会自动退回算子迁移——它要么有迁移可看，要么能明确说出「算子构成没有变化，
这一步改的是语句内部」。手动切换过视角后不再自动退回。

`ExpandMixedKernel` 的家族识别不靠名字前缀：只有当某个函数在**同一个 Pass** 里 kind 翻成
`Group`、且同时新增了 `<name>_aic` / `_aiv` 时才认作拆核。纯前缀匹配会把 `foo` 和 `foo_0`
这种编译器加后缀区分出的**不同** callable 误当成父子（两份 run 实测误伤 0 例）。

设计依据是仓库里已有的结论 [`Design/llvm-flow/Pass_Diff_对话记录_20260908.md`](../llvm-flow/Pass_Diff_对话记录_20260908.md)：
文本 IR Diff 是事实来源，Graph 负责快速理解结构，两者同步；并且**不存在一种计算图能解释所有 Pass**，
所以每个 Pass 自带「推荐视角」。

## 为什么 Diff 和图在浏览器里现算

`lib/*.mjs` 既是构建期代码，也被打包进 `lib/bundle.js` 供页面使用——**同一份解析器**。
页面加载一份快照原文后自己解析、自己 diff、自己建图，因此任意函数、任意视角、任意 Pass
都能全保真查看，而不需要把几十万行预计算结果冻进数据包。解析一份 5000 行快照约 50ms，最近 8 份缓存在内存里。

## 五种结构图

节点按 union 布局**一次性排好**，再按状态着色（新增 / 删除 / 属性改变 / 未变）。
分别给前后两版单独布局会让插入一个节点就把整张图挪位，真正的变化反而被淹没。

| 视角 | 节点 | 最适合看 |
| --- | --- | --- |
| 调用 / 作用域 | 函数 | `InlineFunctions`、`Outline*`、`ExpandMixedKernel` |
| 控制流 | for / if / with 区域 | `UnrollLoops`、`LowerPipelineLoops`、`SkewCrossCorePipeline` |
| 数据流 | SSA def-use | `ConvertTensorToTileOps`、`LowerCompositeOps`、`ResolveBackendOpLayouts` |
| 任务 DAG | `pl.submit` / `pl.at` 及依赖边 | `AutoDeriveTaskDependencies`、通信相关 Pass |
| 内存布局 | 缓冲区、空间、地址 | `InitMemRef`、`MemoryReuse`、`AllocateMemoryAddr` |

任务依赖是抽象解释 `pl.array.create` / `update_element` 链恢复出来的——依赖在 IR 里是通过
`_submit_deps_buf` 数组传递的，不解释这些语句就拿不到真实的 task DAG。

## 「高频改写」如何工作

有些 Pass 不改任何结构指标，只是就地改写每条语句——`AllocateMemoryAddr` 填 MemRef 偏移、
`ConvertToSSA` 追加版本后缀、`CanonicalizeIOOrder` 把 `pipeline` 降成 `range`。
这类 Pass 如果只报「735 行变化」等于什么都没说。

所以构建期会把被改写的行按 token 重叠度**配对**（相似度低于 0.5 的算纯增删，不硬凑），
再对每一对做 token 级 diff，聚合出最高频的替换。例如：

```
AllocateMemoryAddr   735 行就地改写，最高频 `0` → `1024`（119 处）
DeriveCallDirections  42 行就地改写，最高频 插入 `, attrs={"arg_directions": [...]}`
MemoryReuse          tile.alloc 668 → 211，合计 11.0 MiB → 4.59 MiB
```

## 已知边界

- `repo/pto` 镜像里缺少部分 Pass 的文档与源码（`BlockNzTensorViews`、`InsertCommFence`、
  `LowerPipelineToSlots` 等）。这些 Pass 的说明面板会明确标注「镜像里没有」，实测证据不受影响。
- MemRef 的 `size` 为 0 且 shape 含动态维时，内存视图显示「动态」而不是「0 B」——
  编译期确实算不出字节数，不应伪装成 0。
- 数据流视角每个函数最多 600 个节点、控制流 900 个，超出会标注「已截断」。
- 两份 run 的 Pass 序列不同（`l3_decode_csa` 52 个、`decode_fwd_layers` 42 个），
  这是编译配置差异，不是数据缺失。

## 新增一份 run
