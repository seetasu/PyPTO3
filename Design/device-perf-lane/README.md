# Device Perf Lane

一次 decode 上板执行的性能分析工具：先给四个可切换的优化视角，再用关键路径和设备泳道把候选任务放回真实时间和物理核上。

- 入口：`index.html`；已加入 `launch.html`。
- 数据：`data/perf-lane.json`，由 `scripts/build_perf_lane.mjs` 从 `dfx_outputs/` 生成。
- 直接双击打开即可：数据已内联进 `index.html`，不依赖 `fetch`，也没有外部样式依赖。

## 重建数据

```bash
node Design/device-perf-lane/scripts/build_perf_lane.mjs
```

读 `Data/DeepseekV4/_jit_l3_decode_csa_20260903_010617/dfx_outputs/<rank>/d0/` 下的 `merged_swimlane_*.json`、`deps.json`、`name_map.json`、`chip_swimlane_records.json`，并联 `Design/parallel-lane/data/parallel-lane.json` 取编译期信息。写两份：`data/perf-lane.json` 和 `index.html` 里的内联副本，同一条命令刷新。

脚本按 `<script type="application/json" id="lane-data">` 这个标签定位内联数据，改页面时不要动这一行。

## 读 trace 时必须先做的一件事

`merged_swimlane_*.json` 里**每个块有两条事件**：

```json
{"args":{"event-hint":"Task:r2t2, FuncId:0, CoreId:64","kernel-duration-us":16.62,
         "local_setup_us":3.86,"duration-us":20.48},"ts":22.90,"dur":20.48}
{"args":{"event-hint":"Task:r2t2, FuncId:0, CoreId:64"},"ts":22.64,"dur":21.08}
```

第二条是影子记录，只有 `ts`/`dur`，没有时间分解。不过滤掉它会导致：块数翻倍、核槽位占用翻倍（能超过 100%）、每个耗时序列里混进一半的 0（看起来像"有块没活干"）。

脚本按 `kernel-duration-us !== undefined` 过滤，并用两条断言守住：

1. 保留的事件数 == `chip_swimlane_records.aicore_tasks.length`（4038）
2. 每次提交的块数 == `deps.block_num`；Group 任务是 AIC 等于 `block_num`、AIV 等于 `2 × block_num`（一组 = 1 cube + 2 vector）

## 页面结构

单页，自上而下一条线索，底部常驻一条提交带：

| 区域 | 回答什么 |
| ---- | -------- |
| **运行摘要** | 这一次跑了多久、多少次提交、核用掉多少 |
| **四个优化视角** | 关键路径等待 / 尾块浪费 / 启动开销 / 并行波次。点一张卡切换视角，整页随之联动 |
| **关键路径** | 优化哪个才有用。条宽 = 实测跨度，红色 = 单块的纯等待任务 |
| **设备泳道** | 两种视图 + 一层叠加。见下一节 |
| **块耗时分布 · 选中任务** | 左边看这次提交是整体偏斜还是个别掉队（单块任务没有分布，直接给结论）；右边给并行度、耗时构成、搬运量、编译期 `core_num` / FunctionType / 出生 pass 和前后依赖 |
| **全部提交表** | 86 次提交，按波次 / 跨度 / 算时 / setup% / 尾块排序 |
| **提交带（常驻底部）** | 86 次提交按设备时序排成一条，红块 = 当前视角的候选，白块 = 当前选中。点任意一块跳过去 |

主体是**一次提交**（一个 taskId + 一个 leaf kernel）。点视角卡、点提交带、点关键路径的段、点泳道条块、点表格行，五者联动。

## 设备泳道

泳道有两个先天难题：行多（24 AIC + 48 AIV = 72 行）、块多（4038 个）。直接铺开只会得到一片噪声。所以拆成「两种视图 + 一层叠加」。

### 视图一：按 Task（默认）

把 86 次提交按核类型贪心装箱——一个 Task 放进第一条「上一个 Task 已经结束」的轨道——于是 **72 行压成 12 轨**（AIC 6 + AIV 6）。轨数 = 该类型同时在跑的 Task 峰值，不是人为设定的。

一条 bar = 一次提交：

| 通道 | 编码 |
| ---- | ---- |
| 条宽 | Task 跨度（`startUs → endUs`） |
| 条高 | `coresUsed ÷ 该类型可用核数`，底边对齐，最小 2px |
| 条内文字 | 够宽（>46px）时直接写 kernel 名 |

**条高是这个视图的重点。** rank0 最长的 Task `cp_token_allgather_payload_wait`（1.08 ms）只占 1/48 个核，画出来是一条又长又细的线；`qk_pv_aiv`（0.89 ms）占满 48/48，是一个满格方块。「跨度长」和「吃核多」被分成两个视觉通道，不会混为一谈。

`coresUsed` 已核对过：86 次提交的 `coresUsed` 与 block 事件里实际出现的 distinct CoreId 数完全一致。

### 视图二：按物理核

原来的 72 行，每行一个真实 CoreId，4038 个 block 平铺。单一灰色 `#565656`，不分核类型色，不画行底纹，行高 9px——它只回答"这次运行长什么样"，用来查某个具体核的空闲分布。

两个视图共用同一套 x 坐标、同一个选中状态和同一层叠加，切换时只换行的组织方式。

### 叠加层（两种视图通用）

从 block 区间扫描出来的结构特征，三组，可逐个关闭：

| 叠加 | 怎么算 | 回答什么 |
| ---- | ------ | -------- |
| **并行宽度** | 对全部 block 做区间扫描（start `+1` / end `−1`，同一时刻先结束后开始），得到并发核数的阶跃函数，再按时间加权聚合成 400 个桶 | 并行度随时间的形状——哪一段塌下去了 |
| **低并行区** | 从同一个阶跃函数里取 ≤2 核的极大区间和 0 核的真空窗，按全高竖带标出并标注时长 | 全机几乎停摆的时间窗在哪、有多长 |
| **地标** | 最长 Task；最长串行段；当前视角 Top1（尾块视角下画的是"拖尾窗口"= 一半块结束 → 最后一块结束） | 三个值得记住的时间区间 |

竖带和并行宽度带共用 x 坐标并贯通全高，所以"曲线塌陷"和"泳道空洞"是同一列，不用来回对照。

由此多出一个 KPI，显示在泳道标题行：**低并行时间占比**（≤2/72 核在跑）。

## rank0 的数据说了什么

| KPI | 值 | 判读 |
| --- | -- | ---- |
| 关键路径上的等待 | **39%**（1.92 / 4.98 ms） | `cp_token_allgather_payload_wait` 单块 1.08 ms、`o_group_a2a_wait` 0.66 ms，零计算纯等 rank 间数据。rank1 同一指标只有 3% —— **rank0 在等 rank1** |
| 低并行时间 | **28.3%**（≤2/72 核在跑） | 其中真空窗（0 核）只有 0.144 ms。rank1 是 11.5% —— 与上一行是同一件事的另一个切面 |
| 核占用率 | 31% | 算 108.9 ms / 容量 347 ms。空闲是真空闲（`duration-us` = `kernel-duration-us` + `local_setup_us`，没有槽内等待） |
| AIC / AIV 每核算时 | 1.54 / 1.50 ms | 两类核负载几乎相等，和硬件 24:48 匹配 |
| 尾块浪费 | 51.1 ms 核时（算时的 47%） | `qk_pv_aiv` 10.7 ms（1.34x，整体偏斜）、`kv_score_proj` 10.0 ms（2.83x 但 p90 贴中位 = 个别掉队） |
| 启动开销 | 15.3% | 小 kernel 密集，`kv_score_proj` 512 块平均每块 9.9 us |
| 波次 | 最多 22 波 | `kv_score_proj` 512 块 / 24 AIC 核；`kv_proj_matmul` 32 块超过 24 核 |
| Task 并发峰值 | AIC 6 / AIV 6 | 86 次提交装箱后只要 12 轨，说明同一时刻在跑的 Task 很少——并行度主要来自单个 Task 内部的 block，不是 Task 之间 |

叠加层带出来的一条读数：rank0 最长的 Task（`cp_token_allgather_payload_wait`，0.21→1.29 ms）**并没有让全机停摆**——最长的串行段是另一处 0.663 ms（3.68→4.34 ms）。所以「39% 的关键路径在等」不等于「39% 的时间全机空转」：等待期间仍有别的 Task 在跑。两个数要分开看。

## 配色约定

整页只用一个彩色。灰阶承载结构，红色只标「当前视角正在说的那件事」：

| 颜色 | 含义 |
| ---- | ---- |
| 红 `#fd5644` | 当前视角的候选任务；关键路径上的纯等待段；块分布里的最慢块；命中候选的核号；当前视角的地标 |
| 白 `#f0f0f0` | 当前选中的那一次提交 |
| 灰 `#565656` | 泳道里的 Task bar / block，不分核类型 |
| 白 5% 竖带 | ≤2 核在跑的低并行区 |
| 红 11% 竖带 | 0 核的真空窗 |
| 其余灰阶 | 网格、核号、地标、并行宽度带 |

核类型、波次、离散度这些维度不再各占一种颜色，需要时看标签、图例和表格。

`vendor/pto-design-system/` 的样式表已不再引用：这套视觉语言与 PTO Design System 不同，且它的 `body{height:100%;overflow:hidden}` 会让页面无法滚动。页面现在自带全部样式。

## 口径与限制

1. 三层时间口径：槽位占用（`duration-us`）、真正计算（`kernel-duration-us`）、启动（`local_setup_us`）。本 run 里前者恰好等于后两者之和，**没有可观测的槽内等待**——数据给不出"核在槽里等什么"。
2. 关键路径按任务实测跨度做最长链，4.98 ms 略大于窗口 4.82 ms：相邻任务在设备上有重叠，链式相加会高估。用它排序，不要当绝对耗时。
3. 尾块浪费 =（最慢块 − 平均块）× 块数，是假设所有块同时启动的核时损失上界。
4. 按 Task 视图里一条 bar 覆盖 `startUs → endUs` 的整段，**中间的空隙也算在内**：多波任务的两波之间如果有间隔，bar 是连续的。要看波与波之间的真实占用，切到按物理核视图。
5. 条高用的是 `coresUsed`，即这个 Task 一生中碰过的 distinct CoreId 数，不是任一瞬间的并发核数。多波任务可能分批占用同样几个核，条高会显示为满格。
6. 并行宽度与低并行区只统计 AICore 的 block 事件。设备上同期的 SDMA、通信等非 AICore 活动不在 trace 的这一部分里，所以「0 核在跑」= 没有 AICore 任务，不等于芯片完全空闲。
7. 搬运量按 `deps.json` 的 tensor shape × dtype 求和，是声明的张量大小，不是实际 GM 读写量。等效带宽只能用于排序。
8. 编译期一侧来自 pass dump；64 个叶子 kernel 与设备 `name_map` 完全对应，86 个 task 的 `block_num` 与编译期 `core_num` 全部一致。43 个任务由 `pl.submit` 提交，本来就没有 `core_num`，表里标为「submit 无」。
9. 只有一次 decode 的 trace，没有基线可比；所有「多/少」都是同一次运行内部的横比。
