# Device Perf Lane

一次 decode 上板执行的性能分析工具：先给四个可切换的优化视角，再用关键路径和设备泳道把候选任务放回真实时间和物理核上。

- 入口：`index.html`；已加入 `launch.html`。
- 数据：`data/perf-lane.json`，由 `scripts/build_perf_lane.mjs` 从 `dfx_outputs/` 生成。
- 直接双击打开即可：数据已内联进 `index.html`，不依赖 `fetch`，也没有外部样式依赖。

## 重建数据

```bash
node Design/device-perf-lane/scripts/build_perf_lane.mjs
```

读 `Data/DeepseekV4/_jit_l3_decode_csa_20260903_010617/dfx_outputs/<rank>/d0/` 下的 `merged_swimlane_*.json`、`deps.json`、`name_map.json`、`chip_swimlane_records.json`，并联 `Design/parallel-lane/data/parallel-lane.json` 取编译期信息。写两份：`data/perf-lane.json` 和 `index.html` 里的内联副本，同一条命令刷新。

脚本按 `<script type="application/json" id="lane-data">` 这个标签定位内联数据，改页面时不要动这一行。

## 读 trace 时必须先做的一件事

`merged_swimlane_*.json` 里**每个块有两条事件**：

```json
{"args":{"event-hint":"Task:r2t2, FuncId:0, CoreId:64","kernel-duration-us":16.62,
         "local_setup_us":3.86,"duration-us":20.48},"ts":22.90,"dur":20.48}
{"args":{"event-hint":"Task:r2t2, FuncId:0, CoreId:64"},"ts":22.64,"dur":21.08}
```

第二条是影子记录，只有 `ts`/`dur`，没有时间分解。不过滤掉它会导致：块数翻倍、核槽位占用翻倍（能超过 100%）、每个耗时序列里混进一半的 0（看起来像"有块没活干"）。

脚本按 `kernel-duration-us !== undefined` 过滤，并用两条断言守住：

1. 保留的事件数 == `chip_swimlane_records.aicore_tasks.length`（4038）
2. 每次提交的块数 == `deps.block_num`；Group 任务是 AIC 等于 `block_num`、AIV 等于 `2 × block_num`（一组 = 1 cube + 2 vector）

## 页面结构

单页，自上而下一条线索，底部常驻一条提交带：

| 区域 | 回答什么 |
| ---- | -------- |
| **运行摘要** | 这一次跑了多久、多少次提交、核用掉多少 |
| **四个优化视角** | 关键路径等待 / 尾块浪费 / 启动开销 / 并行波次。点一张卡切换视角，整页随之联动 |
| **关键路径** | 优化哪个才有用。条宽 = 实测跨度，红色 = 单块的纯等待任务 |
| **设备泳道** | 两种视图 + 一层叠加。见下一节 |
| **块耗时分布 · 选中任务** | 左边看这次提交是整体偏斜还是个别掉队（单块任务没有分布，直接给结论）；右边给并行度、耗时构成、搬运量、编译期 `core_num` / FunctionType / 出生 pass 和前后依赖 |
| **全部提交表** | 86 次提交，按波次 / 跨度 / 算时 / setup% / 尾块排序 |
| **提交带（常驻底部）** | 86 次提交按设备时序排成一条，红块 = 当前视角的候选，白块 = 当前选中。点任意一块跳过去 |

主体是**一次提交**（一个 taskId + 一个 leaf kernel）。点视角卡、点提交带、点关键路径的段、点泳道条块、点表格行，五者联动。

## 设备泳道

泳道有两个先天难题：行多（24 AIC + 48 AIV = 72 行）、块多（4038 个）。直接铺开只会得到一片噪声。所以拆成「两种视图 + 一层叠加」。

### 视图一：按 Task（默认）

把 86 次提交按核类型贪心装箱——一个 Task 放进第一条「上一个 Task 已经结束」的轨道——于是 **72 行压成 12 轨**（AIC 6 + AIV 6）。轨数 = 该类型同时在跑的 Task 峰值，不是人为设定的。

一条 bar = 一次提交：

| 通道 | 编码 |
| ---- | ---- |
| 条宽 | Task 跨度（`startUs → endUs`） |
| 条高 | `coresUsed ÷ 该类型可用核数`，底边对齐，最小 2px |
| 条内文字 | 够宽（>46px）时直接写 kernel 名 |

**条高是这个视图的重点。** rank0 最长的 Task `cp_token_allgather_payload_wait`（1.08 ms）只占 1/48 个核，画出来是一条又长又细的线；`qk_pv_aiv`（0.89 ms）占满 48/48，是一个满格方块。「跨度长」和「吃核多」被分成两个视觉通道，不会混为一谈。

`coresUsed` 已核对过：86 次提交的 `coresUsed` 与 block 事件里实际出现的 distinct CoreId 数完全一致。

### 视图二：按物理核

原来的 72 行，每行一个真实 CoreId，4038 个 block 平铺。单一灰色 `#565656`，不分核类型色，不画行底纹，行高 9px——它只回答"这次运行长什么样"，用来查某个具体核的空闲分布。

两个视图共用同一套 x 坐标、同一个选中状态和同一层叠加，切换时只换行的组织方式。

### 叠加层（两种视图通用）

从 block 区间扫描出来的结构特征，三组，可逐个关闭：

| 叠加 | 怎么算 | 回答什么 |
| ---- | ------ | -------- |
| **并行宽度** | 对全部 block 做区间扫描（start `+1` / end `−1`，同一时刻先结束后开始），得到并发核数的阶跃函数，再按时间加权聚合成 400 个桶 | 并行度随时间的形状——哪一段塌下去了 |
| **低并行区** | 从同一个阶跃函数里取 ≤2 核的极大区间和 0 核的真空窗，以全高灰色纹理标出时间范围，悬停查看时长 | 全机几乎停摆的时间窗在哪、有多长 |
| **地标** | 最长 Task；最长串行段；当前视角 Top1（尾块视角下画的是"拖尾窗口"= 一半块结束 → 最后一块结束） | 三个值得记住的时间区间 |

竖带和并行宽度带共用 x 坐标并贯通全高，所以"曲线塌陷"和"泳道空洞"是同一列，不用来回对照。

由此多出一个 KPI，显示在泳道标题行：**低并行时间占比**（≤2/72 核在跑）。

### Task 抽象层（按物理核视图）

物理核视图可从「Task 分布」单选一种任务分布特征。该图层直接作用于现有物理核上的 block：符合特征的 Task 按 kernel 家族着色，同一 kernel 在不同核心和时间位置保持同色，未命中的 Task 淡化；图例显示主要 kernel 组及命中数量。物理核行数和时间位置不变，也不新增泳道。选择「依赖间隔」时，前驱结束到后继开始之间的观测间隔会叠加在原时间轴上；这些规则用于定位线索，不代表自动判定性能问题。

| 图层 | 筛查规则（当前 rank 内） |
| ---- | ---- |
| 拖尾任务 | 结束时间位于 P90 之后，且 Task 跨度不低于中位数 |
| Task 并行度不足 | 多块、跨度不低于中位数、平均计算并发低于该核类型容量的 25%，且 Setup 占比低于 50% |
| 块负载不均 | 至少 4 块，最大/平均块耗时 ≥1.5，且 P90/中位数 ≥1.4 |
| 尾波空置 | 多波任务的最后一波占用不足该类型可用核数的一半 |
| 离散小 Task | Task 跨度与块数都处于当前 rank 的较低四分位 |
| Setup 占比高 | Setup 占计算与 Setup 总耗时的 30% 以上 |
| 依赖间隔 | 所有可匹配前驱中，最晚结束时间到该 Task 开始之间的间隔大于 3 μs 或两倍块 P50（取较大值） |

这些规则用于从当前 trace 中筛查可疑形态，不是性能问题的自动判定。尤其是低并行度、尾波空置和依赖间隔，可能由算法依赖或任务本身的设计决定；需要结合关键路径、Task 语义及其他 rank / 基线数据判断。

## rank0 的数据说了什么

| KPI | 值 | 判读 |
| --- | -- | ---- |
| 关键路径上的等待 | **39%**（1.92 / 4.98 ms） | `cp_token_allgather_payload_wait` 单块 1.08 ms、`o_group_a2a_wait` 0.66 ms，零计算纯等 rank 间数据。rank1 同一指标只有 3% —— **rank0 在等 rank1** |
| 低并行时间 | **28.3%**（≤2/72 核在跑） | 其中真空窗（0 核）只有 0.144 ms。rank1 是 11.5% —— 与上一行是同一件事的另一个切面 |
| 核占用率 | 31% | 算 108.9 ms / 容量 347 ms。空闲是真空闲（`duration-us` = `kernel-duration-us` + `local_setup_us`，没有槽内等待） |
| AIC / AIV 每核算时 | 1.54 / 1.50 ms | 两类核负载几乎相等，和硬件 24:48 匹配 |

| 启动开销 | 15.3% | 小 kernel 密集，`kv_score_proj` 512 块平均每块 9.9 us |

叠加层带出来的一条读数：rank0 最长的 Task（`cp_token_allgather_payload_wait`，0.21→1.29 ms）**并没有让全机停摆**——最长的串行段是另一处 0.663 ms（3.68→4.34 ms）。所以「39% 的关键路径在等」不等于「39% 的时间全机空转」：等待期间仍有别的 Task 在跑。两个数要分开看。

## 配色约定

整页只用一个彩色。灰阶承载结构，红色只标「当前视角正在说的那件事」：

| 颜色 | 含义 |
| ---- | ---- |
| 红 `#fd5644` | 当前视角的候选任务；关键路径上的纯等待段；块分布里的最慢块；命中候选的核号；当前视角的地标 |
| 白 `#f0f0f0` | 当前选中的那一次提交 |
| 灰 `#565656` | 泳道里的 Task bar / block，不分核类型 |
| 灰色斜纹竖带 + 顶部虚线短标记 | ≤2 核在跑的低并行区，作为时间背景，不画 Task 包络式边框或浮签 |
| 灰色点纹竖带 + 顶部实线短标记 | 0 核的真空窗，与低并行及潜在关注点分开表达 |
| 其余灰阶 | 网格、核号、地标、并行宽度带 |

核类型、波次、离散度这些维度不再各占一种颜色，需要时看标签、图例和表格。

`vendor/pto-design-system/` 的样式表已不再引用：这套视觉语言与 PTO Design System 不同，且它的 `body{height:100%;overflow:hidden}` 会让页面无法滚动。页面现在自带全部样式。

## 口径与限制

1. 三层时间口径：槽位占用（`duration-us`）、真正计算（`kernel-duration-us`）、启动（`local_setup_us`）。本 run 里前者恰好等于后两者之和，**没有可观测的槽内等待**——数据给不出"核在槽里等什么"。
2. 关键路径按任务实测跨度做最长链，4.98 ms 略大于窗口 4.82 ms：相邻任务在设备上有重叠，链式相加会高估。用它排序，不要当绝对耗时。
3. 尾块浪费 =（最慢块 − 平均块）× 块数，是假设所有块同时启动的核时损失上界。
4. 按 Task 视图里一条 bar 覆盖 `startUs → endUs` 的整段，**中间的空隙也算在内**：多波任务的两波之间如果有间隔，bar 是连续的。要看波与波之间的真实占用，切到按物理核视图。
5. 条高用的是 `coresUsed`，即这个 Task 一生中碰过的 distinct CoreId 数，不是任一瞬间的并发核数。多波任务可能分批占用同样几个核，条高会显示为满格。
6. 并行宽度与低并行区只统计 AICore 的 block 事件。设备上同期的 SDMA、通信等非 AICore 活动不在 trace 的这一部分里，所以「0 核在跑」= 没有 AICore 任务，不等于芯片完全空闲。
7. 搬运量按 `deps.json` 的 tensor shape × dtype 求和，是声明的张量大小，不是实际 GM 读写量。等效带宽只能用于排序。
8. 编译期一侧来自 pass dump；64 个叶子 kernel 与设备 `name_map` 完全对应，86 个 task 的 `block_num` 与编译期 `core_num` 全部一致。43 个任务由 `pl.submit` 提交，本来就没有 `core_num`，表里标为「submit 无」。
9. 只有一次 decode 的 trace，没有基线可比；所有「多/少」都是同一次运行内部的横比。

## 关注点的 Pass 分析

Pass 步骤默认展示对象的前后结构图，并用边框区分保留、新增、改写、复用与告警。点击对象会同时高亮前后快照，显示该对象的属性变化；展开「关联原始代码」只查看匹配片段。完整解释、快照和告警收进折叠区域。依赖图可单独切换前端 / P09 / P10 / P40；核内图显示循环展开、具体值的缓冲复用，以及 Put 路径上的 Fence 插入。`pass-objects.js` 是基于现有摘录策划的结构示意，不表示实测指令时间或重叠。

`csa_merge_pack_publish` 默认先进入「Setup 归因与 Pass 依赖」：48 个 block 的交互时序图展示领取到真实 kernel 开始的执行前区间、kernel 执行区间与 qk_pv 最后执行结束参考线；点击 block 更新本核前驱结束、领取和执行时间。下一步展示约 99% 的区间覆盖量，再追溯前端、P09、P10、P39 / P40 中保留的显式依赖。原始周期按归档时钟频率换算，支持两个 rank；覆盖比例不等于独立采集的等待计数。

「在泳道中查看 qk_pv 前驱」会选中前驱、展开任务详情，并调整时间范围覆盖前驱和当前任务。csa 卡片入口改为「查看等待归因」，仅展示执行前等待及依赖来源。

### 独立编译诊断：P35 MemoryReuse

侧面板增加独立于五个运行时关注点的入口「P35 MemoryReuse · 流水隔离深度 2 → 1」。该案例没有运行时 Setup 指标，也不提供高 Setup 到缓冲退化的归因链接。四步视图为：

1. **请求与诊断**：P29 stage=2 与 PH-MR-001 的实际隔离深度 1，展示两阶段独立存储到共享存储的结构变化，不表示实测执行时间。
2. **缓冲映射**：按相同 SSA 名称匹配 P34 / P35，阶段取自 P34 的 pipeline_membership。可选择 mem_vec_15、mem_vec_27、mem_vec_56、mem_vec_19，点击计算值联动两侧高亮及原始代码。默认 mem_vec_15 展示四个 32 KiB 计算值由四个物理缓冲合为一个，其中包含 stage 0 与 stage 1；view 别名不重复列出。
3. **容量解释**：单组请求 64 KiB，小于扣保留区后的 184 KiB 可规划容量；诊断明确报告整体同驻资源压力。没有绘制未经记录的峰值占用，也没有将终态分配总量当作失败候选的峰值证明。
4. **证据与影响**：区分已确认的结构退化与待验证的峰值冲突集合、指令停顿、对照收益。资源约束下的回退尚未被认定为编译器缺陷。

数据由 scripts/build_memory_reuse_case.mjs 从原始归档生成，渲染与交互在 memory-reuse-case.js；原始诊断及 PTO 位置映射可展开查看。页面保持本地静态加载。

`qr_hadamard_matmul` 与 `qr_hadamard_quant` 同样提供「查看 Pass 分析」入口：

- Matmul：前端 64 行切分 → P11 / P17 的 tile 规模 → P19 的 Mat / Left / Right 空间与最终布局 → PH001 输入搬运告警及 C++ 指令。
- Quant：前端两轮读取 → P11 的加载与舍入转换链 → P35 缓冲复用 → 最终布局、读写粒度告警及 C++ 两轮加载。

两类分析用表格展示静态形状、数据路径、字节数和布局，关联原始告警与 PTO 源码位置；运行摘要显示当前 rank 的平均计算并行度和最慢 / 平均块比值。静态字节数、粒度建议不能当作实际 GM 流量、带宽或慢块原因。

三个 kernel 的任务详情抽屉也提供同一入口，即使切换 rank 后未进入推荐前五，仍可从泳道选中该任务打开；关闭分析后返回原来的任务详情。推荐卡片入口则返回对应卡片。

`pass-analysis.css` 为局部样式，`data/pass-analysis.js` 是可直接在 `file://` 下加载的证据数据，无需网络请求。更新归档或摘录范围后运行：

```bash
node Design/device-perf-lane/scripts/build_pass_analysis.mjs
```

该脚本只生成按 kernel 索引的 Pass 证据文件，不重建性能 trace、不改写页面内联数据。摘录范围与解释为人工策划，归档变化后需重新核对。

## qk_pv_aic / qk_pv_aiv：#2080 方法改编

桌面布局下，性能分析栏左边界支持拖动宽度，普通分析与 Pass 分析共用并记忆用户设置。双击分隔条或按 Enter / Home 恢复默认；分隔条聚焦后左右键以 16px 调整，Shift 配合方向键以 48px 调整。宽度范围随工作区约束，Pass 分析最小 360px，普通分析最小 260px，最大 800px，并为主泳道保留至少 480px。窄屏及收起状态隐藏拖动条；拖动期间不重建泳道，结束后精确重绘。

### AIC / AIV 分片依赖与写回

依赖结构来自 `25_after_SplitVectorKernel.py`：AIC L1877 推送 QK 分数，L1879 接收 AIV 返回的 BF16 P，再执行 PV；AIV L1925 接收分数、L1936 返回 P。分数为 32×128 FP32（16 KiB），P 为 exp 后的局部权重 32×128 BF16（8 KiB），未在此处完成最终归一化。正常有效分支的 O 由 AIC 写入 sparse_blk_oi，m/l 由 AIV 写入 sparse_blk_mi / sparse_blk_li；无效分支的 AIV 零值写回不在这条演示分支中展开。

当前分片组的两个分片分别以虚线箭头串联 QK→发送分数→关联 AIV、P 返回→接收 P→PV；当前分片的箭头提亮，配对分片保留灰色箭头。等待使用灰色斜纹。同轮依赖事件同步提亮，直接选择事件为白描边。右侧依赖图、等待按钮、事件卡及写回分支均可反向定位；O 与 m/l 分开显示，不推定二者写回的先后顺序。Q 搬运仍独立联动原有 InferTileMemorySpace 外提结构。

### 按最终代码展示跨分片执行

AIC 以 16 个分片组组织原有 32 个演示分片，每组两个分片的 CUBE 顺序为 QK₀ → QK₁ → PV₀ → PV₁（后续组依次编号）。最终生成的 `kernels/aic/qk_pv_aic.cpp` L535、L626 先后推送两份 QK 结果，L636、L756 分别接收两份 P 后执行各自 PV；这决定顺序与分片匹配，不提供事件时间。

模拟排布中，AIC 计算下一分片 QK 时，关联 AIV 可处理前一分片的分数；AIC 只在发出两个 QK 后依次消费 P₀/P₁。每个分片仍满足 score push → AIV 计算 → P push → P pop → PV，O 写回归 AIC，m/l 写回归 AIV。事件时间按每组预算缩放，保持所选 block 的总区间不变，重叠和等待的具体长度仍为示意。32 分片与 16 组是 Demo 规模，不声称是该 block 实际执行次数。

泳道上方的组内顺序条可点击选择 QK/PV 分片，右侧依赖页与 PV 分析也展示该顺序；选中组使用浅灰背景定位，两条分片依赖链同时可见，当前分片高亮。CUBE 事件在放大后显示 QK/PV 与分片编号，窄事件保留悬停名称。组内切换、轮次导航、红色 Q 搬运的 Pass 外提联动及收起恢复保持原行为。

### DeepSeek Block 分析的信息组织

右侧不再并列计算、Pass、条件、验证四个页签。顶部只固定 Core、执行耗时和返回操作，「计算过程」「详细信息」默认折叠；计算阶段点击仍可定位事件和对应 Pass。正文顺序固定为当前事件卡 → 一句关注点 → P19/P23-P25/P28/P30 阶段导航 → 当前阶段前后图 → 折叠的检查条件与待验证项。事件卡显示分片与轮次，具体事件时间保留在悬停信息中，避免重复 Core 与时间。

P19 保留加载外提结构、重播及默认折叠的代码依据；P28 保留在 Pass 后泳道内直接重排，不增加独立示意图。去掉重复阶段标题、变化说明和另一个 P19 跳转入口，避免一页出现多条并列分析路径。当前关注点、检查内容随所选 Pass 更新。计算过程与验证折叠区的展开状态在事件/阶段切换时保留；主泳道选择、Core、轮次与原计时不变。Paged Attention 的三种数据来源及其 Pass 分析不受本次重组影响。

### 连续 Pass 演变画布

DeepSeek Block 分析现在使用一张固定对象身份的 SVG 画布，依次为 P19 → P23 → P25 → P28 → P30。P19 演示将重复 Q 从循环中提到驻留位置并转为复用；P23 将向量计算移到 AIV、显现分数/P 跨核依赖；P25 加入 AIV subblock 有效形状；P28 将 QK₁ 从 PV₀ 后移到前方并保持逐分片依赖；P30 保持主顺序、显现内部 L0 展开。P19 标为候选假设，其后为结构参考，不声称整条候选链已在真实 kernel 上验证。

控制条支持播放全过程、暂停/继续、本阶段重播；阶段滑块范围 0（Pass 前）至 5（P30），可连续拖动到阶段中间位置，五个阶段按钮可直接定位。播放只修改当前画布节点和依赖线属性，不重建主泳道或当前画布 DOM；暂停保留几何位置。依赖端点随节点同步插值，主泳道保留原选择并按当前阶段高亮相关操作。播放及拖动不改变核时间、KPI 或分片选择。

前后对照默认折叠，展开后显示当前阶段前后两张快照；源码链接跟随阶段更新。切换主泳道事件会中止播放并自动定位到相关阶段：Q/KV → P19；分数/P 传递 → P23；AIV 向量 → P25；QK/PV/等待 → P28；L0/最终展开 → P30。阶段节点内选中对象反向联动主泳道，同一分片身份贯穿各阶段。窗口缩放、关闭分析或切换场景取消播放并清理临时高亮；减少动态效果时直接定位最终阶段，滑块仍可手动定位。实现位于 qk-pass-evolution.js；原 P19/P28 单阶段辅助函数保留作来源参考，不再作为默认独立画面或自动动画入口。

### 连续播放的逐阶段改动聚焦

画布按当前 Pass 区分改动、关联与上下文：P19 聚焦 Q 加载/复用及其消费连线；P23 聚焦拆出的 VEC、分数与 P 传递，新增跨侧依赖用实线；P25 聚焦 subblock 有效形状及 VEC 范围，不暗示新的执行重排；P28 仅将下一分片 QK 与前一分片 PV 视为主重排对象，相关 AIV/P 消费作为次级上下文，跟随端点的依赖仍用虚线表示关系未变；P30 聚焦 CUBE 内部展开分隔，主顺序及依赖保持。其余对象降低透明度，鼠标和键盘仍可选择。主泳道同步区分主改动与关联事件，保留原始选中态。

每段运动约 1.4 秒，落位后停留 1.2 秒，再进入下一阶段；停留时显示一句本步结果。暂停/继续保留剩余停留时间；拖动或直接定位阶段不强制等待，重播本阶段同样保留落位停留。停留期间不重复更新 SVG 几何，帧内不重建画布或主泳道。全部五阶段（含末阶段）均停留后结束，减少动态效果时直接显示最终结构。说明只解释候选/编译结构变化，不表示实际设备耗时或优化收益。
