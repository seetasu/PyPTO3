# PyPTO 层次化语义计算图
## 产品概念与交互设计原则

**研究对象：** `pypto-lib/models/qwen3_14b/paged_attention_pypto.py`  
**设计主题：** AI 生成算子的理解与探索（AI-generated Operator Comprehension）  
**方案名称：** Hierarchical Semantic Computation Graph（层次化语义计算图）

---

## 1. 背景与目标

AI 已经能够生成复杂的算子实现，用户的工作正在从手动编写代码，逐渐扩展到理解、审查、修改和优化 AI 生成的代码。

以 Qwen3-14B 的 `paged_attention_pypto.py` 为例，875 行源码集中实现了 Q/K Norm、RoPE、KV Cache Append 和 Paged Attention，并包含数据分块、AIC/AIV 协同、流水线及同步机制。

用户阅读这类代码时，需要同时理解算法逻辑、数据关系与底层执行方式。传统源码阅读方式要求用户自行识别语义边界、重建数据依赖，并将分散的实现细节关联成完整的计算模型。

**设计目标：将长篇算子源码转换为可逐层探索、可回溯到源码的计算语义模型，降低从代码到计算理解的认知成本。**

核心用户问题包括：

1. 这个算子完成什么计算，输入和输出是什么？
2. 核心计算由哪些阶段组成，阶段之间存在什么依赖？
3. Tensor 在计算过程中如何生成、变化、传递与使用？
4. 某个计算阶段为什么需要这些操作、状态和中间数据？
5. 如何从抽象计算快速定位到实际代码，并进一步验证实现？

## 2. 核心概念：层次化语义计算图

Hierarchical Semantic Computation Graph 是按计算语义及依赖关系组织、支持不同粒度探索的计算图。

它包含两种核心关系：

- **计算依赖关系：** 操作和数据之间的生产、消费及状态依赖。
- **抽象层级关系：** 一个高层计算模块可以细化为多个具有内部依赖的计算单元。

例如，对本案例可以建立如下语义层级：

**Level 1：Paged Attention Pipeline**

展示 Q/K/V Preparation、KV Cache、QK Matmul、Online Softmax、PV Matmul 与 Output 之间的关系。

**Level 2：Online Softmax**

展示 Row Maximum、Rescale、Exponential、Normalization Sum 以及跨 Stack 的状态传递。

**Level 3：具体计算实现**

进一步解释相关数学表达式、PyPTO 操作及数据变换。

层级深度根据计算复杂度和用户理解需求确定，不要求所有节点具有相同的展开层数。

### 2.1 计算语义层级与源码结构的关系

语义计算图不等同于函数调用图、AST 或源代码执行步骤列表。

一个源码函数可能包含多个具有独立意义的计算模块；一个计算模块也可能对应多个不连续的源码区间。

本案例的主体位于一个大型 JIT inline 函数中，但可以按照 Q/K/V Preparation、Cache Append、QK、Softmax、PV 等计算职责划分为多个语义模块。

因此，**计算图的分组依据是计算职责与依赖关系，源码位置用于建立映射和验证，不直接决定图的层级。**

## 3. 三个相互关联的理解维度

复杂算子的理解可以从计算语义、数据组织和执行调度三个维度展开。

| 维度 | 核心问题 | 本案例中的内容 |
|---|---|---|
| 计算语义（What） | 算了什么，为什么需要这些操作？ | Q/K Norm、RoPE、QK、Softmax、PV |
| 数据组织（Data） | 数据怎样被组织、变换和使用？ | Tensor Shape、GQA、KV Page、Stack、Transfer Buffer |
| 执行调度（How） | 计算如何映射到硬件并协调执行？ | SPMD、AIC/AIV、事件同步、软件流水线 |

三个维度共享相同的计算对象，但关注的关系不同。

默认计算图以计算语义及必要的数据依赖为主，帮助用户建立算法理解。数据组织和执行调度可以作为关联视角或按需展开的补充信息。

**可泛化原则：同一复杂系统可以从不同维度观察，但应保持对象身份与语义一致，避免让用户在切换视角时重新建立整个 mental model。**

## 4. 计算图的信息模型

### 4.1 节点：表达具有明确意义的计算实体

从用户理解的角度，可以区分以下几类实体：

| 实体 | 含义 | 示例 |
|---|---|---|
| Operation | 对数据执行的计算或变换 | RMSNorm、Matmul、Exp、Row Sum |
| Data | 被生产、变换、传递或使用的数据 | Q、K、V、Scores、Probability、Tensor |
| State | 在迭代过程中持续更新的计算状态 | Online Softmax 的 m、l_sum、o |
| Composite Operation | 可进一步分解的语义计算模块 | Online Softmax、Q/K Norm + RoPE |
| Region | 具有共同控制或计算范围的结构 | Stack Loop、条件分支、并行区域 |

这些是信息语义类别，不强制对应某一种视觉形状或颜色。

同一个对象在不同粒度下可以有不同的表达方式。例如 Online Softmax 在一级图中作为整体计算节点，在二级图中表现为包含多个 Operation、Data 和 State 的子图。

### 4.2 连线：表达真实关系

计算图的连接关系需要具有明确含义，至少区分：

- 数据生产与消费：某个 Operation 产生的数据被其他 Operation 使用。
- 计算依赖：某个计算需要其他计算的结果。
- 状态依赖：当前迭代依赖上一轮保存的状态。
- 控制或同步依赖：在对应视角中解释执行顺序、条件或同步约束。

不能因为两段代码相邻，就默认它们之间存在计算依赖。

例如本案例的 Q 和 K 预处理具有不同的数据路径，不应该仅根据源码排列顺序画成前后依赖。

### 4.3 抽象粒度：只提升有助于理解的信息

并非每一个 Scalar、Tensor 临时变量和 API 调用都需要成为独立节点。

决定是否提升为节点时，应考虑：

- 是否具有独立的计算职责？
- 是否是理解主要数据关系的关键对象？
- 是否形成重要的分支、汇合或状态反馈？
- 是否能够帮助解释当前模块的设计意图？
- 是否具有进一步展开的理解价值？

低价值细节可以保留在属性说明、源码映射或更深层级中。

## 5. 层次化展开与折叠规则

### 5.1 展开是语义细化

展开一个 Composite Operation，应当揭示它内部更细粒度的计算关系。

例如：

Online Softmax → Update Maximum、Rescale、Exponential、Normalization Sum。

展开前后使用相同的节点与连线语义。不能在外层使用计算依赖图，展开后变成按代码行号排序的步骤列表。

### 5.2 保持父子图的语义边界

父节点应当具有可以理解的输入、输出和计算职责。

展开子图后，内部可以出现更多操作、状态及中间数据，但它与外部计算之间的主要输入输出关系应当保持一致。

以 Online Softmax 为例：

- 外部输入：当前 Stack 的 Scores，以及上轮累积状态。
- 内部计算：Maximum、Rescale、Exp、Sum。
- 外部输出：Attention Probability，以及更新后的状态。

概率数据继续参与 PV 计算；更新的状态继续参与后续 Stack。

对于存在共享数据、原地更新或跨模块依赖的复杂场景，边界可以保留必要的外部引用，不能为了图形整洁而删除真实依赖。

### 5.3 允许非线性结构

统一规则需要覆盖多种计算关系：

- **分支：** 一个计算结果被多个下游操作消费。
- **汇合：** 一个计算同时依赖多个输入。
- **循环：** 一组操作重复执行，并可能携带状态。
- **条件：** 根据条件选择不同的计算路径。
- **并行：** 多组计算在依赖允许的条件下并行执行。
- **状态反馈：** 后续迭代依赖之前的中间状态。

因此，并非所有计算图都是简单的无环图。对于循环和状态反馈，应使用明确的迭代范围与状态关系，避免错误地线性化。

### 5.4 允许不均匀深度

不同模块的内部复杂度不同。

本案例中，QK Matmul 可以较简单地表达数学计算，而 Online Softmax 需要解释跨 Stack 的最大值、归一化分母和输出累积状态。

二者无需强制具有相同的展开深度。

**可泛化原则：展开层级取决于用户理解所需的语义复杂度，不取决于代码行数、函数数量或固定的信息架构模板。**

## 6. 基于 Paged Attention 的计算抽象示例

### 6.1 一级：算法总览

本案例的一级计算关系可概括为：

1. Q、K、V 分别完成必要的预处理。
2. K/V 写入对应的 Paged KV Cache。
3. Q 与从 Cache 分页读取的 K 参与 QK Matmul。
4. Scores 经过 Scaling、Mask 和 Online Softmax。
5. Probability 与 Cache 中的 V 参与 PV Matmul。
6. 跨 Stack 累积 Context，完成归一化后输出。

一级图应突出 Q/K/V 的独立输入路径、KV Cache 的作用，以及 QK、Softmax、PV 的依赖关系。

这是算法语义的抽象，不代表实际硬件按同样顺序串行执行。

### 6.2 二级：Online Softmax

Online Softmax 的主要计算涉及：

- 初始化跨 Stack 状态。
- 计算当前 Stack 的 Score 最大值。
- 更新累计最大值。
- 根据最大值变化计算 Rescale。
- 计算当前 Stack 的指数概率。
- 更新归一化分母。
- 输出供 PV 计算使用的概率数据。
- 维护下一轮计算需要的状态。

这里最重要的结构不是八个步骤的顺序，而是：

**Scores 与历史状态共同决定新状态；新状态影响概率和归一化；概率流向 PV；更新后的状态继续参与后续迭代。**

具体的延迟 Rescale FIFO 和事件同步属于进一步理解执行实现时的重要内容。

### 6.3 三级：源码与具体计算

用户继续深入时，可以看到：

- 数学表达式与对应 PyPTO 操作。
- Tensor 或 Tile 的输入输出。
- 相关 Shape、Dtype 及存储属性。
- 对应源码区间。
- 特定实现方式的原因及限制。

这一层应区分代码中明确存在的行为、根据算法推导的解释，以及需要实际运行才能验证的判断。

## 7. 通用交互原则

### 7.1 Overview First，Details on Demand

默认呈现足以理解主要计算的语义总览。用户通过局部展开查看更细粒度的关系。

不要求用户阅读完整代码，或一次性理解全部底层运算。

### 7.2 Focus + Context

展开局部计算时，保留与上游、下游的关联。

当内部结构过大时，可以进入聚焦视图，但仍应告知用户当前处于哪个父模块、输入来自哪里、输出流向哪里。

### 7.3 Consistent Graph Grammar

同一类型的实体和关系在不同层级保持一致的含义。

展开改变信息粒度，不改变用户对节点、边和依赖的基本理解方式。

视觉样式可以迭代，但图语义不能随层级任意变化。

### 7.4 Bidirectional Source Mapping

图中的计算对象应能够对应到相关源码，源码中的关键操作也能够关联到语义图。

映射可以是一对一、一对多或多对多。

例如一个语义模块可能对应多个不连续的源码区间，不能简单假设每个计算节点都对应连续的代码块。

### 7.5 Semantic Continuity

用户从高层进入低层后，必须能够识别：

- 当前展开的是哪个计算模块？
- 当前子图与父节点有什么关系？
- 哪些输入来自父图外部？
- 哪些数据输出给下游？
- 哪些状态在内部持续更新？

这保证用户在多次展开后仍能保持空间与语义定位。

## 8. 可泛化的计算语义抽象方法

虽然本案例是 Paged Attention，但该框架应适用于其他算子。通用化重点不在于规定所有算子使用相同节点，而在于采用一致的分析方法。

### 8.1 先识别计算契约

明确一个算子的输入、输出、主要计算目标，以及 Shape、Dtype、数值和执行环境等约束。

这是确定图边界的基础。

### 8.2 再识别主要计算阶段

根据算法目的将实现划分为具有独立职责的模块。

例如：

| 算子类型 | 可能的一级语义模块 |
|---|---|
| Matmul | 输入准备、分块计算、累加、输出 |
| Softmax | Reduce Max、Exp、Reduce Sum、Normalize |
| LayerNorm | 统计量计算、归一化、仿射变换 |
| Paged Attention | QKV Preparation、Cache、QK、Softmax、PV、Output |
| MoE | Routing、Token Dispatch、Expert Compute、Combine |
| Reduction | 数据分组、局部归约、跨块归约、输出 |

以上是通用语义拆分示例，实际结构应以具体实现为准，不作为固定模板。

### 8.3 根据依赖建立图结构

识别每个模块的输入、输出、生产者、消费者，以及必要的状态与控制关系。

优先依据数据和计算依赖确定连接，而不是按照源码顺序生成箭头。

### 8.4 根据理解价值决定分解深度

优先细化具有复杂数据组织、数值稳定性处理、并行结构、循环状态或特殊实现策略的模块。

对简单操作不强制继续分解。

### 8.5 关联实现证据

每个重要计算模块应保留与实际源码的关联。

语义解释应当有依据；对于源码无法独立证明的性能收益、硬件执行结果或算法正确性，应明确说明需要进一步验证。

## 9. 产品边界与后续扩展

本阶段的核心任务是 **Code Comprehension（代码理解）**，即帮助用户建立对算子实现的可解释 mental model。

它与后续三个任务具有连续性：

- **Code Review：** 判断 AI 生成的计算结构是否符合需求与约束。
- **Correctness Debugging：** 将静态计算关系关联实际 Tensor 值、异常数据和传播路径。
- **Performance Analysis：** 将语义计算阶段关联编译结果、Runtime Task、硬件执行时间与性能瓶颈。

但静态语义图本身不能证明算子正确或性能最优。

后续可以在相同计算模型上连接 IR、Trace、Args Dump、PMU 等证据，扩展其解释和诊断能力。

## 10. 设计原则与验收方向

这套能力应遵循以下原则：

1. **语义优先：** 首先帮助用户理解计算目的和关系。
2. **依赖驱动：** 图的连接由真实计算与数据关系决定。
3. **层级一致：** 父图和子图使用统一的语义规则。
4. **接口连续：** 展开前后保留正确的输入输出关系。
5. **按需深入：** 复杂度随用户探索逐步释放。
6. **源码可追溯：** 重要解释均可回到真实代码。
7. **结构可泛化：** 适用于不同算子、不同计算结构和不同展开深度。
8. **事实与推断分离：** 算法解释、源码事实、运行结果具有不同的证据等级。

设计验收应重点观察用户能否完成以下任务：

- 快速描述算子的主要计算过程。
- 准确识别关键数据的来源和去向。
- 理解一个复杂计算模块的内部依赖。
- 展开和收起子图时保持对整体计算的认知。
- 定位某个语义操作对应的源码。
- 区分计算逻辑、数据组织和执行实现。
- 从计算结构中识别值得进一步检查或验证的区域。

## 总结

**Hierarchical Semantic Computation Graph 的价值，是将代码中的计算知识组织成可逐层理解的结构。**

它不要求源码本身具有清晰的函数拆分，也不要求所有算子遵循相同的计算步骤。

通过统一的计算实体、依赖关系、语义分组和层次化展开规则，用户可以从整体算法逐步进入具体实现，同时保持对输入、输出、数据关系和源码位置的理解。

对于 PyPTO，这可以成为连接 AI 代码生成、代码理解、实现审查，以及后续计算可观测与诊断能力的基础交互模型。
