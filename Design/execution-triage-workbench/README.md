# Execution Triage · DSpark Serving

DSpark Serving（DeepSeek-V4-Flash w8a8，16 NPU）的性能定界 demo，从一轮压测的整体分布下钻到一个 decode step。

| 页面 | 作用 | 数据 |
|---|---|---|
| `overview.html` · 压测总览 | 256 个请求的分布、输出波次与关键 KPI | GBS256 压测 `result3.json` |
| `index.html` · 单请求定界 | 全程 / 单步两种泳道 + 关键路径、设备分布、优化队列 | GBS1 单请求 STRACE（lane 专项里的算子级下钻另取 GBS256 的 profiler trace，页面标明） |
| `device.html` · 设备详情 | 一张卡的算子级分析：66 步总览 + 多流甘特 + 算子排行 + 逐步趋势 | GBS256 压测包里的 Ascend profiler trace（单卡，另一次采集） |
| `core.html` · 核级泳道 | 一张卡 60 个核（20 AIC + 40 AIV）的任务铺排、kernel / setup 拆分、任务依赖 | PyPTO L2 swimlane（**Qwen3 TP1 prefill**，第三份数据） |
| `analysis.html` · 详细分析 | 关键路径三段条、Step 节奏、单步瀑布、层详情 | 同上（GBS1 STRACE） |

两份数据是两次独立采集：

- 总览页来自 `Data/dsv4-flash-dspark-a3-dp4tp4ep16-gbs256-in256o64.zip` 里的 `result3.json`（vLLM `benchmark_serving` 的客户端口径，256 并发、输入 256 / 输出 64 tokens）。同一压缩包里还有 1.38 GB 的 profiler trace，**总览页没有用到**；它只被单请求页 lane 专项里的「算子级下钻」用到（见下文，并在页面上标明不是同一次采集）。
- 单请求页来自 `Data/serving-strace-swimlane(2).json`（服务端 STRACE，GBS1）。Serving、Worker 和 16 条 Host STRACE lane 共用 host `CLOCK_MONOTONIC`。
- 所以**总览页上点任一请求进入的单请求页，是另一次采集的示例**，不是那个请求自己的 trace。

### 总览页口径

- **时间原点**取最早的 `start_times`；`ttfts` / `itls` 都是秒，页面统一换成毫秒。全部 256 个请求在 37.5 ms 内提交完毕（`request_rate: inf`）。
- **首 token 批次**：把 256 个首 token 时刻按间隔 200 ms 断开聚类，得到 4 批（1 / 102 / 123 / 30 个请求）。prefill 是分批做的，不是一个一个做的。
- **输出波次**：把全部 14,240 个输出时刻按间隔 40 ms 断开聚类，得到 67 波，每波几乎都是全部在跑的请求一起吐出一段。以 400 ms 为界分成慢波段（29 波，间隔 P50 777 ms，覆盖窗口 82%）和快波段（38 波，间隔 P50 122 ms，覆盖 16%）。
- **波间隔为什么在 23.00 s 变快，这份数据不能回答**。候选解释至少有两个：采集时开着的 PyTorch profiler 在前段放大了每步耗时（同一压缩包的 trace 有 645 万条事件、跨度 74 s，而压测窗口只有 27.4 s）；或者服务端在那一刻改变了调度。**页面只陈述这个拐点，不标注原因**；要定论需要一份对齐到同一时钟的服务端 trace。
- `mock-server-trace.json` 是为了演示如何与客户端波次对照而编写的**合成示例**，不是这次压测采集的服务端 trace。它构造了一种假设：慢段的 worker dispatch 到 device start 之间存在较长等待，快段该等待消失，而 device 耗时近似不变。该示例只能说明真实 trace 可如何帮助区分 host 等待与 device 执行，不能作为 23 秒拐点原因的证据。
- **输出间隔双峰**正是上面两段的直接结果：6,724 个间隔 >400 ms（中位 777 ms），7,516 个 ≤400 ms（中位 121 ms）。所以均值 433 ms 和中位 135 ms 差了 3 倍，看均值会误判。
- **TPOT** 用 `benchmark_serving` 的口径 `(E2E − TTFT) / (output_tokens − 1)`，横跨两个波段，因此 P50 386 ms 不代表任何一段的真实步长。
- **投机解码**：99,680 个草稿 token 只有 1,990 个被接受（2.0%），接受长度 1.14；逐位置接受率从 9.1% 掉到 0.1%。这是客户端汇总字段，不是从 trace 里算的。
- **服务曲线的口径**：每 250 ms 一个采样点；速率与分位用 1 s 滑动窗口（相当于 `rate[1s]`）。
  - **输出速率的单位是“段/s”**，即每秒到达客户端的输出块数，不是 token/s。投机解码让一段可能带多个 token，这次全程平均 1.13 token/段。
  - **排队中 / 生成中**以首 token 为界：请求发出后到首 token 之前算排队，之后算生成。
  - **KV cache 利用率**的占用量按“每个生成中的请求占住 prompt 256 token + 已生成的部分”算；分母取这套部署的可用槽位 102,400 token。
  - **TTFT 达标率**的 2 s 阈值是这个 demo 设的，不是业务 SLO。
- **16 rank 视图的口径**：`result3.json` 只有客户端数据，没有 rank 维度，所以这一层按 DP4 TP4 EP16 的拓扑建模：
  - 每个 rank 一个专家路由份额（r6 最高，高于均值 33%），份额决定它每步到达同步屏障的比例，最晚到达的 rank 定义这一步的长度，其余 rank 的剩余时间记为等待。
  - 每步的步长取该时刻的输出间隔 P50，所以立方体随光标切换时与服务曲线、波段划分是一致的。
  - 通信占比随路由份额上升（承载多的 rank alltoall 更重）。忙碌时间再拆四项：Attention 与 TP AllReduce 各 rank 绝对耗时相同（每步 25% / 8.5%），剩余计算归 MoE 专家、剩余通信归 EP AlltoAll（`ranks.sum[].mix`）；256 个路由专家按 EP16 均分，每卡 16 个。
  - 同一压缩包里的 profiler trace 只采了 **1 个 rank**：进程元数据只有 1 个 Python 主机进程，设备侧全部标为 `NPU 0`，通信任务的 `src rank` 全为 0；点对点任务的对端只有 rank 1–3（一个 4 卡组）。所以它无法替换这 16 个 rank 的构成，最多能给 rank 0 一张卡的计算 / 通信 / 空闲分项。
- **E2E 分布很窄**（P50 26.84 s，最快 20.57 s）：请求是同步成批推进的，单个请求的快慢基本由整批决定。

## 单请求定界（`index.html`）

页面上只放数字、标签和图形，口径说明都记录在本文件中。瓶颈口径对齐 [pypto-serving#95](https://github.com/hw-native-sys/pypto-serving/issues/95)（DeepSeek V4 8 卡 serving 性能验证与瓶颈分析）：该 issue 把 `bind` 里的 Device 分配 + H2D 列为 P0，本页用 GBS1 的 STRACE 把同一笔账拆到单个 decode step 上。

- **左上 · 这次请求的结果**
  - 大字 E2E 12.57 s，右侧是口径（53 次输出 · 非流式 max_tokens 128）与四个数：首次输出 421 ms、输出间隔 P50 225 ms / P90 266 ms、冷启动 407 ms。
  - 结果层只说明问题有多大，定位要靠下面的关键路径拆分。
- **左中 · 构成**（始终描述泳道当前展示的范围，不是固定均值）
  - 全程视图给 `decode 52 步 · 平均 233 ms（P50 224 · P90 265）`；Serving / Host / Device 泳道标题旁显示 52 个 Decode step 的累计分项时间与平均每步时间，Device 数值标为上界。单步视图仍在顶部显示 `D47 · 224 ms（52 步均值 233 ms）` 的步级构成，Prefill 与 Draft init 标注“不计入均值”。
  - **下钻到异常步时，这一行末尾多一个红徽章**：`超 P90 · 比中位多 54.2 ms，多在 Device +48.9 ms`——单步视图一打开就回答“我为什么在这一步”，不用自己和中位做减法。正常步没有这个徽章。
  - 三行 Serving / Host / Device **相加等于这一步的周期**，百分比也按这一步算（Host 含 Worker 下发）。所以步与步的差异看得见：D47 是 0 / 102 / 122 ms，而流水未热的 D01 是 2.18 / 224 / 136 ms。点击某一行选中对应那条带，右栏切到“逐步构成”。
  - Host 行下挂一条子项 **bind.args · 分配 + H2D**，标注“可消除”——这是 #95 的 P0 项，不是整个 Host。
  - 子项另显示“设备内存分配 / H2D 搬运”估计，逐 lane、逐 step 按固定比例拆分，且相加保持为原 `bind.args` 时长。
  - 子项下再挂一行 **lane 启动 · 其他**（不标红，它不是可消除项）：两行相加 = Host 层减去 Worker 下发，所以“Host 里除了 bind 还有多少”不用去右栏的表里找。
  - 最后一行 **权重 / Cache 常驻后**：把这一步关键路径上的 bind.args 去掉、其余阶段不变的**推算**，不是实测。下面补一行量级：全程视图给 `每步 −45% · 本请求累计 −5.45 s`，单步视图给 `每步 −N% · 这一步 −N ms`。
  - 全体统计不在这里，而在右栏“关键路径”表（52 步的均值 / P50 / P90 / 最大）。
- **中间 · 泳道（两种范围，共用三条带与同一套行名）**
  - x 只表示时间，y 只表示层与 lane，所以**同一时刻在所有行上垂直对齐**，一条竖线就能读出此刻每层在做什么。
  - 三条带从上到下：Serving（调度器）、Host（16 条 host lane 的 bind）、Device（16 张卡的 runner_run）。
  - **横轴两端对齐**：时间轴长度按容器比例实时计算，让 viewBox 与容器同比例，图不会被居中缩放后在两侧留白；左边留的是 lane 行名，右边留的是注记，都不是空白。
  - **带内上下留白对称**：留白统一为 `PAD_IN`，Host 带里 Worker 那几行的位置只有单步视图才留——全程视图没有 Worker 行，留着会把 16 条 lane 顶到底边、顶部空一块。
  - **Worker 是三行，不是一行**（单步视图）：worker 进程里有三个线程在并发跑，行名取它们各自的职责，线程名挂在行名的 `title` 上：

    | 行 | 线程 | 跑的调用 |
    |---|---|---|
    | 准备 | `MainThread` | `prepare_decode` |
    | 下发 | `pypto-device` | `dispatch_decode`、`execute_step`、`batch_prefill` |
    | 回收 | `pypto-output` | `reclaim_decode` |

    这三件事**真的在同时发生**：`prepare_decode` 有 97% 的时间与 `reclaim_decode` 重叠，53 次里 51 次完全落在某个 reclaim 区间内部；`dispatch_decode` 是 98%、52/53。压在一行里它们会相互覆盖，长条看起来像被切成两段——所以按线程分行，和 Host 带「一条 lane 一行」是同一套规则。读法也因此变直白：**一边回收第 N 步的输出，一边准备并下发第 N+1 步**。
  - **同一个线程里还有调用栈嵌套**就再往下铺一行（`execute_step` 里套着 `batch_prefill`，只在 Prefill / Draft init / D01 出现），悬停标注“嵌套调用”。行高按这一步实际需要的层数算，不固定留空。
  - **带名独占每条带上方一行**（`[2] Host · 每卡一条 host lane`），左侧栏只放 lane 行名，两者不再挤在同一块地方。
  - **行名：Host 用 `lane N`，Device 用 `dev N`**。STRACE 的 lane 是 host 侧线程，**每张卡一条**（`cat` 为 `strace.host`，`tid === args.device`，trace 里的线程名恰好也叫 `device N`，所以照搬线程名反而分不开两者）。Host 行画的是这条线程的 `bind.args`——在 Device 上分配内存并 H2D，调用方与耗时都在 Host，但工作按卡拆分；Device 行画同一条线程的 `runner_run`，代表那张卡的执行窗口。同编号上下对齐，可以直接读“lane 6 bind 结束 → dev 6 的 runner_run 开始”。

- 状态写在 hash 里（`#lane=6&step=S37&sort=ms&op=28`），可以直接分享到某一步的某个算子。
- 这一页**不与左边那套估计值混算**：它回答“设备上到底跑了什么、等了多久”，而 `index.html` 的 `runner_run ≤ 124 ms`、`执行 110 ms / 等待 12 ms` 是另一次采集上的上界与推算，两者口径不同，不能相加。
- 头部第二行是再往下一层的入口（`core.html`）——但那是**第三份数据**，见下。

## 核级泳道（`core.html`）

“传统的单卡 AIC-AIV 泳道”这类图，**GBS256 的 Ascend trace 做不到**：那份导出里单元类型只是任务上的一个 `Task Type` 标签，没有 `aic_time` / `aiv_time`，而且同一条流上的任务严格串行（实测相邻任务最大重叠 0.001 ms，纯属四舍五入），按单元拆成两行也不会有并发。

能做到的是仓库里另一份数据：**PyPTO 自己的 L2 swimlane 导出**。

| | |
|---|---|
| 来源 | `Data/pypto_qwen3_profiles/pypto_qwen3_profiles/tp1/swimlane/prefill.json`（39 MB） |
| 模型 / 阶段 | **Qwen3 · TP1**，一次 **prefill** 的 L2 调用 |
| 与谁的关系 | 和 `index.html`（DSpark GBS1 STRACE）、`device.html`（DSpark GBS256 profiler trace）**既不同模型也不同采集**，三者不能对齐、不能相加 |
| 规模 | 60 个核（20 AIC + 40 AIV）· 窗口 44.42 ms · 15,228 个核上任务 / 684 个 SPMD 任务 · 18 种算子 |
| 时间 | 核上周期计数（50 MHz），trace 原值 |

- **为什么用 prefill 不用 decode**：同目录 `decode.json` 的 `FuncId` 全是 `-1`，任务名只有 `task(r2t0)` 这样的 token，映射不到算子名；prefill 的 `FuncId` 有值，事件名本身就是 `gate_up_proj_spmd(r1t5)`，18 种算子都能认出来。这一条写在页面的口径折叠里。
- **主图**：一行一个核，上面 20 个 AIC、下面 40 个 AIV，中间留一条缝。实色是 `kernel-duration-us`，紧跟着的红色一小截是 `local_setup_us`（下发开销）。滚轮缩放、拖动平移，`重置缩放` 回到全窗口；范围写进 hash（`#r=12.416,15.469`）。
- **一眼能看出的事**：AIC 20 个核平均占用 **72.2%**（kernel 合计 641 ms），AIV 40 个核只有 **6.89%**（122 ms）——这次 prefill 的算力几乎全压在立方核上，向量核大部分时间空着。
- **算子表**：18 种，按 kernel 合计排；给实例数、kernel、setup、用了几个核。`gate_up_proj` 一项就占 352 ms，而且它的 **setup 12.8 ms 比别的算子高一个量级**（其余都在 1 ms 上下），表里 setup 占比超 3% 的标红。
- **任务依赖**：点泳道里任一任务，右下给它的 `fanin` / `fanout`（例如 `gate_up_proj (r3t284)` 上游 `post_rmsnorm (r3t276)`、下游 `silu (r3t285)`），可以顺着依赖一跳跳地走。SPMD 任务会同时落在 20–60 个核上，选中时整列一起亮。
- **没用到的**：同目录 `deps.json` 还有 684 个任务的张量形状 / dtype / stride 与依赖边，`l2_swimlane_records.json` 有原始周期计数与 AICPU 调度阶段；这一页都没用。
  - **优化队列**：P0 权重 / Cache 常驻、P1 lane 6 bind 偏慢、P1 Device 临界路径、P2 冷启动移出请求路径；每项的“当前”列都取自本次基线。下方是复测时要确认的四条验证目标，含“不以增加 D2H 为代价”“不覆盖本基线”。
  - **逐步构成**：54 行里两个指标名是一样的，所以**名字只在表头写一次**（例如 `lane N · bind.args / 关键 lane · 分配 + H2D`，逐步会变的那一截写成 `N`，具体值在每格的 `title` 上），行里只留会变的数和一条 16 格的分卡色带（Host 层越红越慢，lane 6 那一格几乎每行都是红的）。超 P90 的那几行**左缘一条红边、step 号标红**（悬停给 `超 P90 · 比中位多 54.2 ms · Device +48.9 ms`），所以在这张 54 行的表里也能直接找到异常步。标题后面跟这一层的口径（`Host · 每个 step　关键 lane 进入 runner_run 之前的时间`），色带每格的 `title` 也带上口径与卡号（`D47 · lane 6 · 进入 runner_run 前 105 ms · 本步最晚进入`）。点击任一格即在中间显示那一步，支持 ↑ / ↓ 切换。
- **右上 ↗**：打开详细分析页。**右上 ↑**：返回压测总览。
- **打开时不预选 step**：默认是全程视图，构成行给 52 步均值；时间线、泳道、「逐步构成」列表、以及右上角跳转详细分析的链接都不带任何一步，hash 里也没有 `step`。点时间线任一段、点全程图里的某一步、或点右栏「逐步构成」的卡片，才会选定一步并切到单步视图。从单步切回全程时，刚看过的那一步仍在图上标出，但构成行回到均值。
- 状态写在 URL hash 里（`#view=…&layer=…&step=…&tab=…`，未选步时没有 `step`），可以直接分享。
- 窄屏下泳道整体缩小，细节需要在桌面宽度查看。

### 颜色约定

- **红 = 告警**：关键路径、关键 lane（`lane 6` / `dev 6`）、超过 decode P90 的 step、已定位的瓶颈项（`bind.args 可消除`、P0）。
- **白 = 选中**：选中的层、选中的 step（时间线上的那一段、全程图上的那一列）、悬停聚焦。选中态不占用红色。
- 其余全是灰阶与线框；未拆分的 Prefill / Draft init `runner_run` 用中灰整块表示“这是未拆分的上界”。
- **拆分段都不是直接测量值**：Device 泳道的亮实色是执行估计，深色虚边是等待估计；设备分布图里的斜纹 / 空档也采用相同口径。完整 `runner_run` 时间窗来自 trace，拆分来自 Demo 模型，不能把估值当作实测执行时间或等待时间。

## 口径

- **step 的边界**：每个 step 从上一步结束算到本步 16 条 lane 全部结束。16 条 lane 在 runner_run 末尾同步结束，所以最晚进入 runner_run 的 lane（关键 lane）决定一步的长度。
  - 它进入 runner_run 之前的时间计为 **Host**；step 之间只有 Worker 在工作的空档也计为 Host。
  - 它的 runner_run 计为 **Device**。没有采集 device_wall，runner_run 里含跨卡同步等待，所以是**上界**。
  - 只有调度器在推进的时间计为 **Serving**。调度本身约 0.47 ms/step，已被流水覆盖。
- **异常步与它的归因**：周期 > decode P90（265 ms）的 decode step 记为异常步，`+超出量` = 这一步的周期 − decode P50（224 ms）。归因是把这一步的 `serving / worker / bind.args / lane 启动 / device` 五个实测分项**各自**与 52 步里该分项的中位相减，取为正且最大的一项；次项达到最大项 60% 时两项一起写。
  - 五个分项各自的中位不等于周期的中位，所以**分项差之和不严格等于 `+超出量`**，界面只说“多在哪一层”，不把它们相加。
  - 全部来自 `runtime.byStep`，在前端实时算出，没有引入新的估计或假设；`build-home-data.cjs` 不需要改。
- **起点分散 / 终点分散**：同一步里 16 条 lane 进入 `runner_run` 的最晚与最早之差、结束的最晚与最早之差。前者 101 ms、后者 2.1 ms，说明差别在到达而不在执行。
- **屏障等待**：按“最晚进入者的 lead 减去自己的 lead”计，是**下界**——它只算了因为早到而必然要等的那部分，没有假设各卡算力相同。
- **分卡数值**：Host 层每格 = 这条 lane 从本步起点到进入 runner_run 的时间；Device 层每格 = 这条 lane 的 runner_run（含等待，所以不着色）。
- **单步流转的归属**：本步的 dispatch = 在第一条 lane 开始前结束的最近一次 `dispatch_decode`，其 `step_id` 即本步；`step_id` 更大的 prepare / dispatch 视为“下一步准备”。prefill 与草稿初始化两步没有 dispatch，不画下发箭头。
- **Worker 的行归属**：每个 span 归它自己的 `tid`，行名取 trace 的 `thread_name`，顺序按流水（准备 → 下发 → 回收），都由 `build-home-data.cjs` 写进 `workerRows` 和每个 span 的 `t` 字段，页面不靠调用名猜线程。行内的层号按区间嵌套实时算（同一线程里后开始且未结束的调用往下一层）。
- **请求指标**：
  - 请求是非流式的（`stream: false`，`max_tokens: 128`）。首次输出取服务端第一次 `scheduler.process_step_output`，不是客户端 TTFT。
  - 每次输出都记录为 `new_tokens=1`，每次实际输出的 token 数无法确认，所以给的是“输出间隔”，不是 TPOT。
  - 只统计落在请求窗口内的输出。流水预下发的 D53 在响应返回后才结束，不计入 E2E。
- **关键路径五段**：均值相加等于 step 周期。
  - `bind.args` 只取关键 lane **落在关键路径上**的那段，即 `max(本步起点, bindStart) → bindEnd`；本步起点之前的 bind 属于上一步的并行时间。
  - “lane 启动 · 其他”＝ Host 段减去上面这段，包含 lane 起线程、bind 结束到进入 runner_run 的空档。
- **观察窗口为什么单列**：16 lane 合计、中位 / 最快 lane、最长 runner_run 来自不同 lane，彼此并行；`validate`、`bind.prebuilt`、Worker `dispatch_decode` 与关键路径重叠或已被流水覆盖。它们用于判断“优化后有没有把代价搬到别处”，不能与五段相加。
- **设备执行 / 同步等待拆分是演示估计**：STRACE 只给 runner_run 的总窗口，不含真实 `device_wall`。为让 demo 展示拆分后的分析流程，构建脚本以稳定公式生成约 104–117 ms 的每卡执行估计，并将 runner_run 剩余时间计入同步等待估计；该拆分不是采集结果，不能用于性能结论。Device 泳道和设备分布图均标注“估计”。
- **bind.args 的分配 / H2D 拆分是演示估计**：STRACE 只记录 `bind.args` 总时长，没有分配和拷贝的独立计时。构建脚本按每 step、每 lane 稳定分配 10–17% 给设备内存分配，余量给 H2D；两项之和严格等于原 `bind.args` 总时长。该比例不是采集结果，不能用于性能结论；界面标注为“估计”。
- **“权重 / Cache 常驻后 ≈ 128 ms”是推算**：逐 step 减去上面定义的 bind.args，其余阶段保持不变，再取均值；按本请求 52 个 decode step 累计约 −5.45 s。它只是基线拆分的算术结果，不是优化后实测，也没有考虑常驻实现本身的开销。
- **lane 6 与次慢 lane 对齐**：E2E 预计约 −1.88 s（−15%），作为常驻前的过渡项放在优化队列 P1，详细推导在分析页。

## 数据生成

```bash
node Design/execution-triage-workbench/build-data.cjs          # data.js：详细分析页
node Design/execution-triage-workbench/build-home-data.cjs     # home-data.js：单请求页（依赖 data.js）
node Design/execution-triage-workbench/build-overview-data.cjs # overview-data.js：压测总览页
node Design/execution-triage-workbench/build-ops-data.cjs      # ops-data.js + device-data.js：算子级下钻与设备详情页
node Design/execution-triage-workbench/build-core-data.cjs     # core-data.js：核级泳道（Qwen3 TP1 prefill）
```

前两个脚本只读取 `Data/serving-strace-swimlane(2).json`；第三个只从 GBS256 压缩包里取出 `result3.json`（直接读 ZIP 的中央目录，不整包解压）。

第四个读同一个压缩包里那份 1.38 GB 的 profiler trace：**流式解压 + 正则扫原文**，只挑设备主执行流（`pid 2733163936 / tid 46`）的任务与 7 条旁流的忙碌区间，不整包解压也不落盘，全程约 3 秒、内存峰值几十 MB。产物两份：`ops-data.js` 约 46 KB（侧栏小结，三步）、`device-data.js` 约 650 KB（详情页，全部 66 步）。

第五个读 PyPTO 的 L2 swimlane 导出（39 MB JSON），按 task token 把 SPMD 任务归并成组，产物 `core-data.js` 约 450 KB。脚本会自己用 `--max-old-space-size=4096` 重启一次（源文件解析后占几百 MB）。
