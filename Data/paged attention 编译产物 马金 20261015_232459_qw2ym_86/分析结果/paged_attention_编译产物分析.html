01结论速览

这是一份 PyPTO 端到端编译产物快照（不是性能 profile 报告）：从 Python 前端 IR 一路降到 PTO MLIR、C++ kernel、incore 二进制与编排 .so，并附带一次 DFX swimlane 采集。

  • 产物身份：Qwen3-14B 的 paged attention 融合算子，源码 /data/m00956180/.../models/qwen3_14b/paged_attention_pypto.py，JIT 编译，supported_execution_modes = ["program"]。算子把 Q/K RMSNorm + RoPE + KV cache 写入 + 分页注意力四件事融进一个 24-block SPMD kernel。
  • Pass 管线高度稀疏：60 个 stage 中只有 21 个真正改动了 IR，其余 39 个是 no-op（含 13 个完全逐字节相同的阶段）。IR 规模从 519 行涨到 1885 行，有 3 个"暴增点"。
  • 性能瓶颈不在算力：端到端 177.2 µs 中，真正在 72 个核上跑的只有 ≈53 µs（AIC 均值 35.2 µs / AIV 均值 36.1 µs），前置调度+准备占了 ≈119.5 µs（67%）。当前有效算力利用率约 30%。
  • 核心可优化点：① 24 block 只摊了 16 个 task，8 个 block 空转；② 编排里插了 7 个 dummy phase-fence barrier，把调度拖到 119 µs 才开跑；③ 33 处 256B 内维 tile 搬运未达 512B L2 cache line。

10可优化点与后续动作

优先级问题证据建议动作
P0 7 个 dummy phase-fence barrier 白占调度 编排第 65–98 行；deps.json 中 7 条 kernel_ids=[-1,-1,-1]；dummy(7) 耗时 5.2 µs 本算子独立编译时这 7 个前驱不存在，应让 ExpandManualPhaseFence 在无真实前驱时直接消除 barrier（当前 pass 是 no-op）
P0 24 block 只摊 16 个 task，8 个 block 空转 num_tasks = active_batch × 8 = 16；for task in range(core, num_tasks, 24) → core 16–23 无迭代 block_num 改 16，或把 task 粒度从 1 kv_head 拆成 2 个半 head，让 24 block 满载
P1 Scheduler drain 占 23 µs drain(8) 22.9 µs ×3、drain_prepare(24) 12.4 µs ×3，发生在核开跑之前 检查 drain 与 dispatch 能否流水重叠；或减少一次性的 3.94 MB scratch 首触（提前预热/复用 workspace）
P1 33 处 256 B 内维搬运未达 L2 line perf_hints.log PH001 ×33，其中 K/V page load 14 处每次 32 KB K/V load 内维抬到 256（bf16→512B），利用相邻 kv_head 内存连续；RoPE 的 cos/sin 合并成 [1,128] 一次 load
P1 L0B 打满 100%、L0C 只用 6%，负载极不均衡 右矩阵 64 KB / 64 KB；累加器 8 KB / 128 KB 考虑一次 matmul 覆盖更多 KV page（提高 L0C 复用），把右矩阵分块加载
